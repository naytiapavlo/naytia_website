## 1. 需求

原话拆成五条可验收的要求：

1. 工具箱里新增一个**文档树**工具；
2. 文档**可以被访客访问**（未登录也能读）；
3. **管理员可以编辑、新建文件夹**；
4. 管理员**不需要编辑界面**——给他们**上传文件的权限**就够；
5. 管理员提交的内容作为**合并请求交给超级管理员审核**，审核通过后才真正对访客开放；
6. 首版先把 `C:\Users\Administrator\Desktop\Minecraft\doc` 里的文档放进去。

第 3 条与第 4 条合起来读是：「编辑」= 往树里**增加**内容（新文档、新文件夹），
而不是在线改正文。第 5 条决定了写操作必须有一条与线上内容分离的提案记录——
这一条是整个功能的骨架，ADR-007 第 4 节是它的决策依据。

## 2. 界面：三种身份共用一个页面

页面是 `/docs/`（自成一套的全屏界面，与逆向工作台 `/ida/` 同级）。
工具箱目录里的卡片用 `entryHref` 直接跳过来，**不设 admin 门槛**——
访客本来就要能读，门槛只在写路径上。

```text
┌ 左侧栏（sticky）           ┐ ┌ 正文区 ────────────────────────────────┐
│ 搜索框                     │ │ 面包屑：文档树 / 代码机制分析 / 12 …   │
│ 目录树（可折叠、带篇数）    │ │ 标题 + 格式/可见性/版本/体积/更新时间   │
│ 统计：8 个文件夹 · 120 篇…  │ │ 操作：下载原文件 / 看原始文本 / 申请删除│
│ 身份提示 + 「打开管理面板」 │ │ 正文（Markdown 渲染 / txt·json 纯文本） │
└────────────────────────────┘ │ 本页目录（≥3 个小节时出现）             │
                               └────────────────────────────────────────┘
                               正文区上方（仅 staff）：管理面板
                               ├ 上传文档（分块上传 + 标题 + 摘要 + 可见性）
                               ├ 新建文件夹（名称 + 上级目录 + 可见性）
                               └ 待审队列 / 我的提交（批准·驳回·撤回 + 理由）
```

三个身份的差别只在**多出来的控件**上：

| 身份 | 看到什么 |
| --- | --- |
| 访客 / 会员 | 目录树 + 正文 + 搜索 + 下载。没有任何写入口，没有管理面板 |
| 管理员 admin | 多出「管理面板」：上传、新建文件夹、看自己的投稿状态与审核意见。**没有**批准按钮 |
| 超级管理员 | 管理面板的提示文案换成「你上传的内容会直接发布」，多出**待审队列**与批准/驳回 |

权限只在服务端强制（`/api/docs/*` 的 `require_staff` 与 `role == 'superadmin'` 判定）；
前端隐藏控件只是不给用户「点了报 403」的坏体验，注释里写明了这一点。

## 3. 后端结构

```text
backend/app/models/docs.py     五张表：doc_folders / doc_documents / doc_files
                               / doc_revisions / doc_submissions + next_path_key()
backend/app/docs_storage.py    落盘层：受控目录、文件名清洗、slug、分块上传、内容寻址
backend/app/schemas_docs.py    pydantic 契约（OpenAPI 的唯一事实源）
backend/app/review_flow.py     「提交单 → 目录树」的发布流程（apply_submission）
backend/app/routers/docs.py    公开读 + 管理员提交 + 超管审核（14 个路由）
backend/scripts/import_docs.py 首版资料导入（幂等、可 --dry-run）
backend/tests/test_docs.py     22 项：权限矩阵、审核流、上传边界、可见性绕过
```

关键点，按读代码时会先撞到的顺序：

- **读路径只有一个过滤器**：`routers/docs.py::Viewer`。目录树、正文、搜索、下载
  四条路径全部经过它，所以不会出现「目录里看不到、拿到 id 却能下载」。
  草稿只有两种人能看见：staff（审稿人）与提交人自己。
- **写路径一律走提交单**：管理员的上传与新建文件夹落进 `doc_submissions`（`status='pending'`），
  线上三张表一动不动。超管批准时才由 `apply_submission()` 落库。
- **批准时二次校验**：目标被删、父目录被改、同名路径被占，都会把提交单标成 `rejected`
  并写明原因，而不是写坏目录树。
- **正文不随目录树下发**：`/tree` 只给元数据（标题、格式、体积、更新时间、文件 id），
  进详情页才拉 `/documents/{id}`。120 篇文档的树响应因此只有几十 KB。
- **下载走 `/api/docs/files/{id}/download`**，不是静态目录：先确认这个文件挂在一篇
  「当前观察者能读」的文档上。`storage_path` 永不出现在任何响应里。
- **分块上传**：`POST /uploads` 开会话 → `POST /uploads/{id}/chunks?index=n` 逐片写 `.part`
  → `POST /uploads/{id}/finish` 拼接、算 sha256、按内容寻址落盘。服务端不把整个文件读进内存；
  分片不连续（`chunk_gap`）、声明大小与实际不符（`size_mismatch`）、超限（`file_too_large`）
  都是结构化错误。

### 3.1 数据表

| 表 | 存什么 | 为什么 |
| --- | --- | --- |
| `doc_folders` | `parent_id` + `path_key`（物化路径）+ `visibility` + `is_published` | 同级重名靠唯一索引拦；导入脚本靠 `path_key` 认人 |
| `doc_documents` | `parent_id` / `slug` / `path_key` / 标题 / 摘要 / 格式 / 可见性 / 当前修订与文件指针 | 树节点 + 元数据，正文不在这里 |
| `doc_files` | 清洗后的原名、体积、sha256、相对存储路径、文本内容 | 内容寻址去重，同一份内容只占一份磁盘 |
| `doc_revisions` | 每次发布一条：`revision_no` / 标题 / 正文 / 编辑人 / 说明 | 可回溯「谁在什么时候改成了什么」；正文在库所以能搜 |
| `doc_submissions` | 提案：动作、目标、父目录、标题/名称/摘要、`file_id`、理由、状态、审核人、审核意见 | 审核流程的载体，批准前不碰线上内容 |

`visibility`（谁能读）与 `is_published`（是否已发布）是两个正交维度：
需求只要求「访客可读 + 审核后开放」，但压成一个字段的话，
以后想加一篇「仅内部」的文档就得再改一次表。

## 4. 首版资料导入

`python scripts/import_docs.py`（在 `backend/` 下执行）：

```text
资料来源：C:\Users\Administrator\Desktop\Minecraft\doc
署名账号：站长（superadmin）
新建文件夹   : 8        漏洞bug分析 / 代码机制分析 及其子目录
新建文档     : 120      58 篇 .md、51 篇 .txt、14 篇 .json（同内容去重后 116 个文件）
内容未变跳过 : 123      再次运行是幂等的
新落盘字节   : 858.1 KB
跳过的文件   : 6        5 个 .html（不在收录范围）+ 1 个 .bak
```

几个刻意的取舍：

- **只收 md / txt / json**：需求确认的范围。`.html` 与 `.bak` 会被列进「跳过的文件」，
  而不是静默丢弃。
- **目录先建、文档后放**：先按磁盘目录结构建出全部文件夹（含父级），再放文档，
  所以每篇文档的父目录一定已经存在，不需要「边建边找父级」。
- **幂等**：按 `path_key` 匹配已有文档，内容 sha256 相同就跳过；
  内容变了才追加一个新版本。可以在资料更新后反复运行。
- **导入即已发布**：脚本以超管身份运行，等价于「超管审核通过」。管理员之后上传的内容
  仍然要走提交单审核。
- **`--dry-run`**：预演并回滚，先看清会导入什么。

导入过程中的三个真实缺陷（都已修，值得记下来）：

1. **落盘名被当成了原始文件名**。`save_bytes` 早期只接受一个名字参数，
   导入脚本传的是磁盘路径，于是库里的 `original_name` 变成了
   `9b713c68...ddb0.md` 这种 sha256——下载时给用户的文件名也是这样。
   修法：`save_bytes(original_name, data, *, stored_as=None)` 把「显示名」与「落盘名」分开。
2. **存储被清过之后复用了悬空记录**。库里有一条同摘要的 `doc_files`、磁盘上的文件却没了
   （清理存储、换机器、恢复备份不全），`_persist_file` 仍然复用那条记录，
   结果得到一篇打不开的文档。修法：复用前必须确认文件真的在（`_blob_exists`）。
3. **同一段内容、不同扩展名被当成同一个文件**。`.md` 与 `.txt` 落盘是两个不同后缀的文件，
   去重键必须带上 `doc_format`，否则记录与磁盘文件对不上。

## 6. 第二轮需求：移动文档与删除文档

> 追加需求原话：「增加删除文档和把文档移动到某一个文件夹的功能」。
> 第一版已经有一条**管理员提交删除申请 → 超管批准**的链路（后端有 API，界面上只有一个
> 「申请删除」按钮），这一轮把移动补上，并把这两件事在界面上真正做成能用的功能。

### 6.1 与既有审核纪律的关系（关键设计决定）

第一版定下的规矩是「管理员的改动一律走提交单，超管的动作直接生效」。
新加的两个功能必须落在同一条规矩里，于是按角色分岔、**不按功能分岔**：

| 操作 | 管理员 admin | 超级管理员 |
| --- | --- | --- |
| 移动文档 / 文件夹 | `action=move_doc` / `move_folder` 提交单 | `POST /api/docs/…/move` 立即生效 |
| 删除文档 / 文件夹 | `action=delete_doc` / `delete_folder` 提交单 | `DELETE /api/docs/…` 立即生效 |
| 改标题 / 改文件夹名 | **不做**（正文内容变了要重新上传；改名走超管） | `POST /api/docs/…/rename` 立即生效 |

两条路径**最终调用 `review_flow` 里同一批函数**（`move_document` / `move_folder` /
`rename_document` / `rename_folder` / `rewrite_folder_paths`），所以「审核通过的行为」
与「超管自己动手的行为」不可能不一致。这是刻意的：两条独立实现迟早会漂移，
而漂移出来的差异（比如一边改了子树路径、另一边没改）是最难查的一类缺陷。

超管的直接操作**也写一条 `status=approved` 的提交单**作为审计记录：
目录树是多人共用的东西，「谁在什么时候把这批文档挪走了」必须查得到。
待审队列里 `status=approved` 的记录在界面上显示成「最近记录」。

### 6.2 物化路径的代价：移动文件夹必须重写整棵子树

目录树是「邻接表 + 物化路径」（ADR-007 第 1 条）。移动或重命名文件夹时，
`path_key` 的变化必须**连带整棵子树**：

```text
移动前： 漏洞bug分析/Naytia        → 漏洞bug分析/Naytia/cv45074160_…
移动后： 资料归档/Naytia          → 资料归档/Naytia/cv45074160_…
```

不改子树会怎样？文档的 `path_key` 会指向一条已经不存在的路径。后果不是报错，
而是**导入脚本认不出这些文档**——下次按路径匹配时找不到，于是又插一份新的，
变成「同一篇文档在库里有两份」。所以 `rewrite_folder_paths()` 是唯一实现，
移动、重命名两个入口都必须走它。

顺带补了两条硬约束：

- **不能把文件夹移进自己或自己的子树**（`move_into_self`）：那会让子树成为孤岛，
  显示路径算不出来、`subtree_folder_ids()` 会走进死循环。
  校验在提交时（`_submission_snapshot`）与发布时（`move_folder`）各做一次——
  提交单可能在队列里躺几天，期间目录结构会变。
- **目标位置已有同 slug 的文档时自动加 `-2` 后缀**（`unique_doc_slug`），
  不覆盖目标目录里的同名文档。排除自己的那条路径：否则「把文档移到根目录」会跟
  「它现在这条路径」撞上。

### 6.3 界面

**正文上方的操作行**（staff 可见，标签按角色变）：

```text
[下载原文件（01_速查卡.md）] [移动到…] [改标题] [删除这篇 | 申请删除这篇]
```

**目录树每个节点的「⋯」整理入口**（默认淡出，悬停或键盘聚焦才明显）：

```text
文件夹：移动到别的目录… / 重命名… / 删除（含 N 篇文档）…
文档：  移动到别的文件夹… / 删除这篇文档…
```

两次都是「先选做什么，再填细节」的两步弹窗：

- **移动**：下拉框选目标文件夹（自己与自己的子树被禁用并标出原因）、可填说明。
- **删除**：必须看到后果（「这个文件夹下有 N 篇文档，连同子目录会被一起删除」
  /「删除后目录树与搜索里都会消失，且无法在站内恢复」），理由可选。
- **弹窗里的说明文案按角色变**：超管看到「点确认后立刻生效，访客马上看到新的位置」，
  管理员看到「提交后进入待审队列，超级管理员批准后才会真正移动」。

**为什么自己写弹窗而不是用 `window.prompt`**：原生 prompt 放不下下拉框，
做不了「禁用自己子树」这种选项状态，也没法在同一个弹窗里说清「这个操作立即生效还是需要审核」。

**待审队列里移动类提交单会写明目标位置**（`target_path`，如 `漏洞bug分析/8848yyds`
或「（根目录）」）。否则队列里只有一句「移动文档」，超管没有判断依据。

### 6.4 这一轮的验证

## 7. 顺手修掉的一个阻断性缺陷

联调时发现后端**根本起不来**：

```text
File "backend/app/public_api/router.py", line 14, in <module>
    from ..errors import PublicApiError
ModuleNotFoundError: No module named 'app.errors'
```

`app/errors.py` 不存在（`PublicApiError` 就在同一个包里的 `public_api/errors.py`），
而且 `main.py` 里写的是 `public_api_router.register(app)`——`from .public_api import router`
拿到的是包 `__init__` 导出的 `APIRouter` 实例，那个对象没有 `register` 方法。

这是同期另一项在建功能（开放工具 API，ADR-005）留下的半成品：
运行中的后端进程比这些改动更早启动，所以现场没暴露，但**任何一次重启都会失败**。
本次按最小改动修好：

- `public_api/router.py`：`from ..errors` → `from .errors`（两个符号一起从同包导入）。
- `main.py`：改成 `from .public_api.router import register as register_public_api`，
  调用 `register_public_api(app)`，并写清为什么不能 `from .public_api import router`。

## 8. 已知限制与后续候选

| 限制 | 说明 |
| --- | --- |
| 不做在线编辑正文 | 需求明确「管理员不需要编辑界面」，更新文档走「重新上传 + 提交单」 |
| 管理员不能自行改标题 | 改标题属于「改内容元数据」，超管可直接改；管理员只能重新上传 |
| 管理员不能重命名文件夹 | 重命名要连带重写子树路径、且容易和别的提交撞车，先只给超管 |
| 移动不产生新修订 | 移动只改位置（`parent_id` / `path_key`），正文与修订链不动，历史仍可回溯 |
| 不做行级 diff | 超管批准的依据是标题、摘要、上传者、动作类型、目标位置与正文预览 |
| 无上传配额与限流 | 靠 `NAYTIA_DOCS_MAX_BYTES`（默认 8 MB）与 staff 门槛兜底 |
| 只收文本 | 二进制附件需要缩略图/预览/扫描一整条链路，这一版不碰 |
| 搜索是子串匹配 | 120 篇 / 87 万字节够用；增长到需要分词时再换 FTS5 |
| 删除不清理磁盘 | 文件按内容寻址，同一份内容可能被别处引用；孤儿文件留待将来的清理任务 |

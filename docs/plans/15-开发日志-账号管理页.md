## 1. 需求

原话：「给项目的超级管理员增加一个管理用户列表的界面，可以设置管理员或者取消管理员，
要能根据名字搜索」。拆成四条可验收的要求：

1. 只有超级管理员能用这个界面（权限在服务端判定）；
2. 看到用户列表：名字、当前角色、注册时间；
3. 能**设置**管理员，也能**取消**管理员；
4. 能按名字搜索。

## 2. 先看清楚已有的东西（避免重复造）

动手前先读了一遍现状，结论是**能力早就在，缺的是界面**：

| 已有的 | 缺的 |
| --- | --- |
| `accounts.role`（member / admin / superadmin，ADR-002） | 一个列出用户的地方 |
| `GET /api/admin/accounts`（超管可读） | 按名字搜索 |
| `PUT /api/admin/accounts/{id}/role`（超管可写任意角色） | 「设为/取消管理员」这个**动作**的接口形态 |
| 首个账号即超管的引导规则 | 告诉使用者「谁是超管、谁不能动」的说明 |

所以这次改动**没有数据库迁移**，后端只加了一个查询参数与一个语义化接口。

## 3. 后端：三个决定各修掉一个真实的坑

### 3.1 搜索放服务端（`?q=`）

前端过滤「已加载的那一批」在演示数据上完全够用，但这一页是**管理**界面：
账号数会随时间增长，一旦列表要分页或截断，搜不到就会得出「这个人不存在」的
错误结论——而管理界面里最贵的错误就是「以为某人不在站上」。所以过滤交给 SQL。

配套的两件事：

- **LIKE 通配符转义**。不转义的话，搜一个 `_` 会命中**所有**账号（`_` 在 LIKE 里
  是「任意单字符」），界面上的表现是「搜什么都有」。`%` 与 `\` 同理。
  转义后按 `escape='\'` 交给 SQLAlchemy。库里存的是 `username_key`（注册时已转小写），
  所以大小写不敏感是天然成立的，中文不受影响。
- **前端复筛当前批**。输入到服务端结果返回之间（防抖 220ms），本地先用同一口径
  复筛，界面不会留着明显不匹配的行。两处口径一致靠「同名规则 + 两侧各一组测试」钉住。

### 3.2 「设为管理员」单独开一个接口

现成的 `/role` 接口收任意角色（**包括 `superadmin`**）。如果界面复用它，那么一个
「给不给管理员」的开关，在契约上就具备了把别人提成超管的能力——权限来自界面的
自觉而不是契约，这在权限系统里是不能接受的默认。

于是新增 `PUT /api/admin/accounts/{id}/admin`，体为 `{"enabled": bool}`，服务端
把它映射到 admin ↔ member 两档。`/role` 保留原语义（`allow_superadmin=True`），
两条路径共用同一段目标校验 `_writable_target`，避免其中一条漏判。

顺带修掉一个真会出事的细节：`enabled: "false"`。pydantic 默认的宽松转换会把
这个字符串变成 `False`——听起来没错，但 Python 里**非空字符串是真值**，在别处
（比如直接 `if payload["enabled"]`）就会变成「取消管理员」实际执行了「设为管理员」。
契约上写 `strict=True`，让它在 422 失败，测试里用 `"false" / "true" / 0 / 1 / None`
五组值钉住。

### 3.3 超管档位不在这条路径上动

超管本来就拥有管理员的全部能力，把这一档「降」成管理员是纯粹的权限损失，
只可能来自误操作——而且要连带失去站点配置与账号管理入口。所以 `_writable_target`
默认拒绝改超管（`is_superadmin`），界面上的表现是那一行**没有开关**，只有一句
说明（而不是给一个点了必然失败的按钮）。

与既有的「超管不能改自己」（`self_role_change`，ADR-002）合起来，就是
「场上永远至少留着一个超管」。`/role` 里那道 `_superadmin_count <= 1` 判断
因此是**第二层兜底**：当前从 API 出发不可达（能造成「最后一个超管被降级」的
只有「改自己」，而那条先被拦），等哪天放开「超管可以改自己」，它才成为主力。
这一点在 ADR-010 里写明了，免得后人以为那是一段死代码而删掉。

## 4. 前端：模块 + 独立页面

```text
src/pages/admin/users.astro      /admin/users/ 页面壳（PageHeading + 挂载点）
src/modules/admin-users/
  index.ts                       唯一公开入口
  api.ts                         fetchAccounts(search) / setAdmin(id, enabled)
  rules.ts                       纯规则：匹配口径、角色文案、行可操作性（零 import 依赖）
  ui.ts                          界面：导航入口、工具栏、表格、交互
src/styles/admin-users.css       本页专属样式
```

三个值得记的决定：

- **独立页面，而不是主页那个悬浮面板**。列表要显示名字、角色、注册时间与操作，
  横着排得下一整行；主页右下角那个 340px 的面板塞不进表格，而把主页改成两栏会
  牺牲首页本身的内容。
- **导航入口由客户端按角色插入**（`mountAdminNav`，挂在 `BaseLayout`）。
  `site.nav` 是构建期配置、访客也能拿到，把「账号管理」写进去等于给所有人一个
  点了会看到拒绝的入口。登录后插入、退出后移除，判定同时订阅 `naytia:session`。
- **搜索框在重渲染中原样保留**。表格内容随搜索变化，但工具栏（输入框）是同一个
  DOM 节点——重画输入框会让焦点与光标位置断掉，表现是「刚打两个字就没法继续输入」。

### 顺手拆出来的 `account/roles.ts`

`rules.ts` 要 `Role` 与 `ROLE_LABELS`，最自然的写法是 `from '../account'`。
但那样 `npm test` 会直接失败：测试用 `node --test` 跑 `.ts`，是**只删类型**
（strip-only）模式，而 `account/api.ts` 依赖的 `shared/api-client.ts` 里的
`ApiError` 用了构造函数参数属性（`constructor(public status: number, …)`），
这是该模式明确不支持的语法。

于是把纯词表（`Role` 类型 + `ROLE_LABELS` 文案）拆到 `account/roles.ts`
（零 import），`api.ts` 再导出一次，**account 的公开接口完全不变**，而纯逻辑
文件可以被对照测试覆盖。这不是为了测试而重构：词表本来就与「怎么发请求」无关。

## 5. 界面

```text
账号管理                                    USER MANAGEMENT
按名字找到用户，决定谁能审核站里的内容。

┌ [按名字搜索…        ×]   12 个账号 · 管理员 3 · 超管 1        [刷新] ┐
├──────────────┬──────────┬──────────────┬─────────────────────────┤
│ 用户          │ 角色      │ 注册时间      │ 操作                    │
│ 站长  #1 · 我 │ 超级管理员 │ 2026-09-16 … │ 不能修改自己的角色       │
│ 副站长 #2     │ 超级管理员 │ 2026-09-16 … │ 超管的管理员身份不能取消 │
│ 小明  #3     │ 会员      │ 2026-09-16 … │ [ 设为管理员 ]          │
│ 路人甲 #4     │ 管理员     │ 2026-09-16 … │ [ 取消管理员 ]          │
└──────────────┴──────────┴──────────────┴─────────────────────────┘
权限由服务端判定，这里的按钮只是入口。超管档位不在这里调整…
```

身份的差别很直接：

| 身份 | 看到什么 |
| --- | --- |
| 访客 / 会员 | 一句「这一页只对超级管理员开放」，**不发任何请求**；导航栏没有入口 |
| 超级管理员 | 上表全部；自己的行与超管行只有说明文字，会员/管理员行有开关 |

「取消管理员」会先弹一次确认，话术说清**失去什么**（「退回普通会员，失去内容
审核权限」），而不是只问「你确定吗」。开关完成后**就地改这一行**（不整表重载），
搜索框焦点与滚动位置都不会跳。

| 前端 `tests/admin-users.test.ts`（已进 `npm test`） | 匹配口径、角色文案、`rowCapability` 分支与优先级、确认话术、分档计数 | 18 项全绿 |
| 浏览器 `tests/manual/verify-admin-users.mjs` | 真 Chrome + 真后端 + 真 Astro 服务，三种身份、导航入口、搜索、授予/取消、刷新持久化、确认框取消、控制台 | 24 项全通过 |

关键几条**是端到端验的，不是只信界面**：点「设为管理员」后角色徽章就地翻转，
**整页刷新后仍然是管理员**（证明确实落库，而不是只改了 DOM）；点「取消管理员」
后回到会员；确认框里选「取消」时角色不变（证明没有偷偷发请求）。

浏览器验收脚本自带隔离环境（临时库 + 独立端口 + 临时 Chrome profile），
**不改动任何仓库文件**，跑完自行清理（连跑三次结果一致、无残留进程与临时目录）；
跑法见 `tests/README.md`。它验证的**不是** dist 产物，而是 Astro 开发服务器
（Vite 按需转换）——原因见脚本头部注释：仓库里同一时刻可能有别的改动在飞，
链路验证不该被别人的文件挡住；生产构建是否通过由 `npm run build` 单独负责。

为了在同源条件下验收（会话 Cookie 是 `SameSite=Lax`，跨端口不会被带上），
`astro.config.mjs` 增加了一个**默认关闭**的可选代理：设了 `VITE_API_PROXY_TARGET`
才生效。这不是为验收临时改文件——早先的版本正是「临时改写配置文件再还原」，
结果撞上两类竞态（热重载时序、`process.exit` 不等异步还原），
细节与修法记在 `tests/README.md`，算是这次踩得最久的一个坑。

## 7. 已知边界与顺手记录的两个问题

本功能的边界：

- 搜索是**子串匹配**（不是模糊/拼音/分词），大小写不敏感；没有分页、没有按角色
  或注册时间筛选——账号规模大到需要这些时，`?q=` 这个形态要重新设计。
- 这一页**只**管「是不是管理员」：不能封禁账号、不能改密码、不能删除账号。
- 不能在这一页授予或取消**超管**（ADR-002 的引导规则与邀请码是唯一来源）。
- 前端 `maxLength=16` 与后端 `max_length=64` 不一致是**有意**的：输入框对齐用户名
  上限（16）以免让人输入不可能匹配的词，接口放宽到 64 是为了让「搜索词比任何
  用户名都长」这种正常情况返回空列表，而不是一个 422。

验证过程中撞到并记录下来的两个问题（都不是本功能引入，但会让人误判
「是不是这次改坏了」）：

1. **58 项后端测试因为 Cookie 配置变成 401**。`backend/.env` 里
   `NAYTIA_COOKIE_SECURE=true`（部署形态是 HTTPS 隧道），而测试客户端走明文 http，
   httpx 不会回传 `Secure` Cookie，于是所有「登录后再操作」的用例都变成 401，
   看着像权限体系坏了。修法是在 `backend/tests/conftest.py` 里用
   `os.environ.setdefault("NAYTIA_COOKIE_SECURE", "false")` 钉住夹具环境
   （环境变量优先级高于 `.env`，`setdefault` 给「确实想测 Secure 那一支」留出口）。
   修完这一批用例恢复正常；收尾时整套 pytest 为 **303 项全绿**（其余失败项由
   并行进行的部署/文档改动一并补齐，例如 `test_mcstructure_api.py` 里那条断言
   `/openapi.json` 的用例——docs 已挪到 `/api/docs`，OpenAPI 随之变成
   `/api/openapi.json`）。
2. **另一进程写文件会把开发服务器打挂**。验收脚本最初开着 Vite 的文件监听，
   期间另一次 pytest 运行在 `backend/tests` 下留下临时文件，watch 撞上就 `EBUSY`
   抛 UnhandledRejection——表现是「登录突然全部失败」，看着像功能坏了。
   现在验收用的代理配置一律关掉文件监听（见第 6 节与 `tests/README.md`）。

## 8. 后续候选

- 按角色筛选与分页（账号规模上去之后）。
- 「管理员动作留痕」：谁在什么时候把谁提成了管理员。现在只有 `role` 的最终值，
  没有变更记录——多人协作管理时这条会变成需要。
- 交接流程：站上出现多个超管后，「超管不能被改」这条要连同交接一起重新设计
  （ADR-010 的重新评估条件里写了）。

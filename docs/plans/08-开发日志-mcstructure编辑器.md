# 08 · 开发日志：`.mcstructure` 编辑器（工具箱第三个工具）

日期：2026-09-16
状态：已实装并通过验证。
关联：`01` 第 6 节（工具箱）、`02` 第 5/9 节（工具模块约束、扩展验证）、`03` 第 4/8 节（工具契约、新增工具流程）、
`05` 阶段 3、[`ADR-003`](decisions/ADR-003-基岩版结构文件解析器.md)（`.mcstructure` 格式与解析决策）。

## 1. 需求

工具箱新增一个 `.mcstructure` 文件编辑器，提供**上传、查看、编辑、下载**四项能力，
并且**直接提供两种编辑方式：NBT 树 与 SNBT 文本**，两者都要支持新增 NBT。

选这两种方式的理由：`.mcstructure` 本质就是一棵 NBT 标签树，任何「结构感知」的界面
（二维网格、三维预览）都只是它的一种投影，会漏掉不认识的字段。直接把树和它的文本表示
交出来，能改的东西最全，也不会因为界面没建模就丢数据。

与已有的 `POST /api/mcstructure/*` 解析接口的区别：那个是**服务端只读解析 API**（面向程序调用，
需要上传）；本工具是**浏览器本地编辑器**（文件不出本机，且能写回）。两者都按同一份
[bedrock.dev 格式文档](https://wiki.bedrock.dev/nbt/mcstructure) 实现，各自独立测试，
用同一份真实文件夹具交叉验证。

## 2. 为什么必须在浏览器侧再实现一遍 NBT 读写

`backend/app/nbt_le.py` 已经有一套 Python 的小端 NBT 读取器。这次又在
`src/tools/mcstructure-editor/nbt.ts` 写了一份 TypeScript 的，**且这一份还多了写入器**。理由：

1. **「下载」必须有写入器**，而服务端接口按 ADR-003 明确是只读的（不提供写回/下载）。
2. **04 文档第 5 节**要求文件处理明确是否上传，且项目口径是「计算在浏览器本地完成」。
   编辑器每次都把文件传到服务器再传回来，与这条口径相悖；编辑是高频交互，也不该走网络。
3. 两侧职责不同：服务端那份服务于**程序化只读接口**，前端这份服务于**交互式编辑**。

代价与约束（已记录，避免以后漂移）：

- 格式规则现在有两份实现，**改动必须同时改两边并跑两边测试**。
- 交叉验证靠同一份真实文件夹具：`backend/tests/fixtures/real/sticky-piston-1x1x1.mcstructure`。
  Python 侧在 `backend/tests/test_real_files.py` 断言，TS 侧在 `tests/mcstructure.test.ts` 断言，
  两边期望值相同（尺寸 1×1×1、原点 `[72,59,-10]`、调色板 `minecraft:sticky_piston`、方块实体 `PistonArm`）。

## 3. 实现结构

```text
src/tools/mcstructure-editor/
  nbt.ts         小端 NBT 读取器 + 写入器（纯逻辑，无 DOM）
  structure.ts   .mcstructure 语义层：parse / serialize / 重新派生 / 统计 / 撤销栈
  snbt.ts        SNBT 文本读写：toSnbt / parseSnbt，解析错误带行号列号
  nbt-edit.ts    按路径的树编辑：改值、改类型、增删节点、改名；路径 ↔ 文本互转
  schema.ts      输入校验（文件类型、大小、非空）
  engine.ts      「文件 → 状态」与「状态 → 字节」两个确定性转换
  view.ts        界面：文件区 / 模式页签 / NBT 树 / 节点编辑 / SNBT 文本 / 结构信息
src/styles/mcstructure.css   本工具私有样式（类名前缀 .mcs，不与其他工具冲突）
tests/mcstructure.test.ts    27 项：解析、往返、编辑操作、统计、撤销
tests/snbt.test.ts           29 项：SNBT 序列化、解析、错误定位、往返
```

### 3.1 保留原始 NBT 树（关键设计）

解析时把关注的部分做成视图（尺寸、调色板、层索引），但**写入时改的是那棵原始 NBT 树**，
而不是重新拼一个文件。原因：真实文件的字段比文档列的多，一旦「重新拼」就会静默丢字段。

实测结论：解析真实文件再原样序列化，**字节完全一致**（`tests/mcstructure.test.ts` 的
「往返一致」用例）。这条断言是发现写入器 bug 最有效的手段。

### 3.2 两种编辑方式

界面顶部是两个页签，操作的是**同一棵 NBT 树**（数据只有一份 `state.root`，不存在两边打架）：

**方式一 · NBT 树**

| 能力 | 说明 |
| --- | --- |
| 展开 / 折叠 | 每个节点可展开；大列表只画前 500 项（其余提示用 SNBT 模式看） |
| 改值 | 选中标量节点后按 **SNBT 写法**输值（`1b` / `1L` / `1.0f` …），类型由后缀决定 |
| 改类型 | 下拉切换 12 种 NBT 类型；标量间互转尽量保留数值，转容器则变空 |
| **新增 NBT** | 复合体节点可加任意类型的字段（选类型 + 填名字）；同名覆盖并提示 |
| 新增列表元素 | 空列表先选类型；非空列表按现有元素类型深拷贝一份追加 |
| 改字段名 / 删除 | 复合体字段可改名（保持顺序）；任意非根节点可删除 |
| 路径栏 | 顶部显示当前选中路径，如 `structure.palette.default.block_palette[0].name` |

**方式二 · SNBT 文本**

| 能力 | 说明 |
| --- | --- |
| 整树文本编辑 | 把根复合体序列化成 SNBT，可整段改、整段粘贴 |
| 应用改动 | 解析文本并写回 NBT 树，成功后自动重新派生尺寸/统计 |
| 从树重新生成 | 树里改过之后一键同步（状态栏会提示「树里有更新」） |
| 压成一行 | 紧凑输出，适合复制到聊天框或命令里 |
| 错误定位 | 语法错误报**行号 + 列号 + 出错那一行的原文** |

SNBT 语法按游戏口径实现：类型后缀、`[B;`/`[I;`/`[L;` 三种数组、裸串与带引号字符串、
`true`/`false`（按字节读）。另外容忍两件手写时很常见的东西：**尾随逗号**与
**`//` 行注释**（后者不是游戏语法，但解析器忽略掉更实用）。

### 3.3 NBT 路径编辑（`nbt-edit.ts`）

树编辑用「路径」定位节点（`['structure','palette','default','block_palette',0,'name']`），
而不是把整棵树深拷贝出去再换回来：

- 深拷贝在结构文件上很贵（`block_indices` 每层可能上百万项）；
- 路径定位让「改一个值」的代价与树的大小无关；
- 路径本身就是界面要展示的东西（顶部路径栏），一举两得。

复合体用 `Map` 存，所以**保持插入顺序**是天然的：改名、新增都不会打乱字段顺序。

### 3.4 方块实体与结构原点的处理

- 方块实体（箱子内容、告示牌文字等）**原样保留**；下载时自动同步其绝对坐标：
  真实文件里 `block_entity_data` 的 `x/y/z` 是**绝对世界坐标**（= 结构原点 + 结构内坐标），
  改过原点后这些坐标会不自洽，所以按当前原点重算。只更新文件里本来就有该字段的实体，
  不凭空造字段。注意层级：`position_data` 的一条是
  `{ block_entity_data: {...}, tick_queue_data: [...] }`，`x/y/z` 在**里面那层**
  （这一点是读真实文件才搞清的，最初写错过一次）。
- 改过树之后用 `refreshDerived()` 从现有 root 重新读一遍尺寸/层索引/调色板/方块实体，
  界面统计与下载都基于改后的树；如果树已被改成不合法结构，如实报错但不动已派生的视图。

### 3.5 SNBT 实现中发现的两个真实坑

1. **裸串不能把 `:` 当分隔符**：`minecraft:stone` 若按「冒号即分隔」解析，会被切成
   键 `minecraft`、值 `stone`，整个复合体随之错位。做法是先读到 `,` `]` `}` 或空白，
   键的位置再用第一个 `:` 切分。
2. **类型后缀要双重判断**：`2147483647` 的末位是 `7`，若只看「末尾字符在 b/s/l/f/d 里」
   或只看「去掉末位是不是数字」，都可能把它切开；而 `minecraft:oak_stairs` 以 `s` 结尾，
   只看后缀字母又会把方块名读成短整型。必须**同时**满足「末位是后缀字母」且
   「去掉末位是数字」才算类型后缀。这两条都是被测试逼出来的（见 4.1）。

### 4.2 真实浏览器端到端

脚本：`tests/manual/e2e-mcstructure.mjs`（真实无头 Edge + CDP，非模拟环境）。
覆盖「文件选择 → 宿主懒加载 → 树渲染 → **新增 NBT** → **SNBT 编辑并应用** → 下载 → 离线复解析」全链路。

- 两个页签都在（`NBT 树` / `SNBT 文本`），默认落在树视图；
- 树逐层展开成功：`structure → palette → default → block_palette → [0]`，
  路径栏显示 `structure.palette.default.block_palette[0]`；
- **复合体节点不出现「值」编辑框**（值由子节点决定），只给「新增字段」；
  选中标量节点 `…block_palette[0].name` 才出现值框，值显示 `minecraft:sticky_piston`；
- **新增 NBT**：在根上新增 `EditorTest`（TAG_Int），树里出现该节点、自动选中、
  初值按所选类型给出 `0`，改成 `2026` 后「已修改」标记出现；
- **SNBT**：文本生成 849 字符，含 `format_version`、原点 `72 / 59`、刚新增的
  `EditorTest:2026`，并带类型后缀；改成 `EditorTest:9999, SnbtAdded:"来自 SNBT"` 后
  点「应用改动」无报错，回到树视图确认 **`EditorTest=9999` 与 `SnbtAdded` 都真的进了树**；
- **错误定位**：故意写错 SNBT 得到
  「第 3 行第 6 列：期望一个值，实际遇到「,」」并附出错那一行原文；
- **下载**：浏览器真实落盘，1×1×1 得 557 字节（比原文件大，因为加了两个字段）、
  8×3×8 得 2230 字节；
- 下载物用 Node 侧解析器**离线复解析**：尺寸、结构原点、方块实体全部保持，
  并且**带着树/SNBT 改过的 `EditorTest=9999` 与新增字段**；
- 页面无未捕获异常。

## 5. 已知限制

> **后续变更（2026-09-16）**：本工具上线后，工具箱按需求**移除了区块坐标助手与材料清单助手**，
> 现在只剩 `.mcstructure` 编辑器一个工具。因此第 4.3 节记录的「第三个工具扩展演练」
> 结论仍然成立（演练时前两个工具确实零改动），但**那两个工具已不存在**；
> 当前工具箱的 `registry.ts` / `manifests.ts` 里只有一个登记项。
> 移除只涉及删除目录、删注册项、删对应测试与文档说明，宿主（`_host/`）未改动。

- **没有可视化预览**：不解析贴图/模型，也不画二维网格或三维预览。这是刻意的取舍——
  结构与方块外观交给 SNBT/NBT 树直接编辑，界面不去「猜」用户想改哪一格；
  代价是改 `block_indices` 这类数组时需要自己算下标（路径栏与 `/api/mcstructure/position`
  接口都能帮着换算）。
- **没有撤销/重做**：直接编辑的是 NBT 树，一步改错只能手动改回。浏览器端可以刷新重来
  （文件不入库、不上传）。
- **大列表在树里只显示前 500 项**：其余需要切到 SNBT 文本模式（文本是全量的）。
- **新增方块排列要手填名称**：只能输入 `minecraft:xxx`，没有方块列表或自动补全；
  改调色板后要自己确认 `block_indices` 的下标仍然对得上。
- **删字段不校验结构完整性**：删掉 `size` 或 `block_indices` 后树仍可编辑，但状态栏会提示
  「当前树不构成合法结构」；下载前请自行确认提示消失。
- **输入上限 64 MB**；输出一律为**未压缩**小端 NBT（与游戏导出一致），不提供 gzip 输出。
- **不做结构尺寸缩放/裁剪**：改 `size` 需要同时重排索引，属于独立功能，本次未做。
- 与服务端 Python 解析器**格式规则各有一份**：见第 2 节的约束，改规则要同时改两边。

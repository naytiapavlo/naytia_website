## 0. 封面（第二轮追加的需求）

三句话说完：发帖时可以随帖传一张 **PNG / JPEG / GIF / WebP**（≤5 MB），
列表卡片显示 16:9 缩略图、详情页顶部显示原图，作者与管理员可以删除。

真正需要小心的是**类型判定**：封面是全站唯一把用户上传的字节当「可直接渲染的内容」
发出去的地方（`<img src>` 直接指向本站 origin），所以判据必须是**文件头字节**，
而且**拒绝 SVG**（它能内嵌脚本，浏览器按文档渲染时就是可执行内容）。落到代码里是四件事：

| 位置 | 做了什么 |
| --- | --- |
| `parsers/image_info.py` | 纯标准库识别 PNG/JPEG/GIF/WebP 并读出像素尺寸；认不出就拒绝，不问文件名 |
| `forum_storage.cover_relpath` | 路径白名单只有 `covers/<2 位>/<64 位 hex>.<png\|jpg\|gif\|webp>`，拼不出 `.html`/`.svg` |
| `routers/forum.get_cover` | `Content-Type` 取自入库时按字节判定的结果 + `nosniff` + `Content-Security-Policy: default-src 'none'; sandbox` |
| `forum_covers` 表 | 尺寸与类型都来自字节；宽高回给前端写进 `<img width height>`，避免图片加载完页面跳一下 |

**服务端不做压缩**（不引入 Pillow，与 ADR-003「零第三方解析依赖」同口径），按原图保存；
界面上提示「建议控制在 1 MB 以内」，因为列表每次都会加载它。这是明确的已知限制。

## 2. 关键实现说明

### 材料清单的口径

清单的统计单位是**调色板条目**而不是方块名。同一个 `minecraft:oak_stairs` 带不同
`weirdo_direction` 是两个条目，清单里就分两行——照着搭的时候，玩家要的是
「几块什么朝向的楼梯」，不是一个模糊的名字汇总。

两处容易被误解的地方都在界面上写明了：

- **空气不算材料**。真实文件的调色板里常常就躺着 `minecraft:air`，
  而「要准备 4 块空气」毫无意义。所以清单里剔除空气，但原始计数一个都不藏：
  `placed_blocks` 含空气、`air_blocks` 单列、`air_cells` 单列。
- **比例的分母是材料总数**，不是含空气的非 void 总数。否则「石头占 33% + 楼梯占 22%」
  会让读者以为剩下 45% 是别的东西。

### 渲染载荷为什么是位图而不是面

见 ADR-006 第 3 节。一句话：位图让空气只占 1 bit，而浏览器拿到它就能自己剔面、切层、旋转，
不必每动一下都回服务器。

### 封面的类型判定为什么必须看字节

封面会由本站的 origin 直接提供（`<img src>` 指向 `/api/forum/threads/{id}/cover`），
这是全站唯一一处「用户上传的字节被当成可直接渲染的内容」。如果类型跟文件名走，
一个叫 `cover.png` 的 HTML 就会被浏览器当网页执行——存储型 XSS。

所以 `parsers/image_info.py` **只认文件头**：PNG 签名、JPEG 的 SOI、`GIF87a/89a`、
`RIFF….WEBP`；认出来之后还要能读出尺寸，读不出就按损坏处理。**SVG 一律拒绝**
（能内嵌脚本，要支持得先做完整消毒）。落盘路径的白名单正则里也只有
`png|jpg|gif|webp` 四种形状，拼不出 `.html`。

四种格式的尺寸读取各有各的坑，都写进了测试：

- PNG 定点读 IHDR（16/20 偏移，大端）；
- **JPEG 不能定点读**——元数据段长度不定，真实手机照片的 EXIF 缩略图能有几万字节，
  宽高只有沿段链走到第一个 SOF 才找得到（夹具里专门造了一个 8 KB 的 APP1 段）；
- GIF 是 6 字节签名后的小端宽高；
- WebP 有三种容器：VP8X（24 位小端，值减一）、VP8L（14+14 位打包在 4 字节里）、
  VP8（3 字节帧标签 + 3 字节起始码之后才是宽高）。**长度检查必须按分支各查各的**——
  最小的 VP8 文件只有 28 字节，用一个统一的「至少 30 字节」卡在前面会把它误判成损坏文件
  （这个坑在写夹具时真的踩到了）。

### 3D 绘制的四个优化

按实际收益排序（都在 `voxel.ts` / `voxel-view.ts` 里有注释）：

1. **剔除被邻居挡住的内部面**。5³ 实心立方体有 125 个方块，只有 98 个可见，
   内部 27 个画了也是立刻被覆盖。
2. **只画朝向相机的三个面**。面的可见性只看视线方向的三个分量符号，不必逐面做点积。
3. **相邻同色面合并成一条路径**。体素建筑里大片同色墙体很常见，
   合并后 `fill()` 调用次数通常从几万降到几千。只有**相邻**的同色面才合并
   ——跨过别的颜色合并会破坏画家算法的遮挡关系。
4. **按需重绘**。没有常驻的动画循环；缩放与画布尺寸变化不重算排序，
   只有旋转才重新排序。

## 4. 本轮验证发现的五个真实缺陷

### 4.0 封面被拒时，结构文件已经写进了磁盘（顺序缺陷）

**发现经过**：测试 `test_封面被拒时结构文件也不入库` 断言「一次请求要么全成、要么全不成」，
结果磁盘上留下了一个 `.mcstructure` 孤儿文件——数据库回滚了，文件没删。

**根因**：一次发帖带两个附件时，代码是「解析结构 → **落盘结构** → 校验封面 → 落盘封面」。
顺序错了：校验还没做完就动了磁盘。

**修法**：拆成两段——`prepare_structure` / `prepare_cover` 只做校验与解析（不碰磁盘），
`store_structure` / `store_cover` 只做落盘与建记录。**所有输入验完之后才开始写磁盘**。

内容寻址下孤儿文件本身不算数据不一致（同样内容再上传会直接复用），
但「每次失败上传都漏一个文件」累积起来就是没人能解释的磁盘占用——
这种问题查起来比崩溃更难。

### 4.0b 空文件被报成「什么都没带」

用户选了文件但文件是空的时，原来的实现只判断「读出来的字节是不是空」，
于是一路走到「既没有结构文件也没有封面」的提示。用户对着「什么都没带」
去找自己明明已经选好的文件——这是把人往错的方向指。
现在「字段没传」（`empty_upload`）与「传了但文件是空的」（`empty_file`）是两个错误码。

### 4.1 版块接口不可用时，发帖表单是一个空的下拉框

**发现经过**：站长反馈「发帖子时无法选中板块因为暂时没有」。查下来他的后端还是改动前的
进程（`/api/forum/categories` 返回 404，而 `/api/forum/threads` 是老接口、照常工作），
所以版块清单是空的。

**但这是我的实现问题，不是「他环境不对」**：原来的代码在这里把异常吞掉了——

```ts
.catch(() => { /* 版块取不到时列表页仍然可用 */ });
```

结果是发帖表单照常渲染，里面是一个**空的下拉框**：点开没得选、表单交不上去（提交时报
「请选择一个版块」）、页面上没有任何地方说明为什么。用户只能猜是自己操作错了。
这正好违反了 04 文档第 5 节「失败要可见」的约定。

**修法**：

- 版块加载失败记进 `state.categoriesError`，**不发帖表单就不渲染**；
  改为显示「暂时无法发帖：版块列表没能加载」+ 具体原因 + 「重试加载版块」按钮。
- 列表页同样提示（帖子照样能看能筛选，只是发不了帖），也带重试入口。
- 404 给出**可操作**的说明：「服务端没有版块接口（404）：后端很可能还在运行旧版本，
  重启一次后端即可」；网络层失败则说「连不上后端服务」。这两句是分开的——
  光说「请求失败（404）」对访客和运维都没有帮助。

**回归覆盖**：端到端脚本第 9 步用注入的 `fetch` 包装把这个接口打成 404，
断言「不出现空下拉框」「不出现发布按钮」「有重试按钮」「提示里说明是旧版本」，
再去掉包装验证能恢复。

### 4.2 时间戳丢失 UTC 标记，刚发的帖子显示「8 小时前」

**发现经过**：端到端脚本第 7 步打印卡片元信息，看到刚发表 30 秒的帖子写着
「最后活动 8 小时前」。8 小时正好是东八区的偏移，于是去看接口原文。

**根因**：SQLite 没有原生时间类型，SQLAlchemy 存的是字符串，**读回来时 tzinfo 会丢**。
于是同一个字段有两种形态：刚写入的对象是 tz-aware（序列化带 `Z`），
重新查一次走「字符串读回」路径就变成 naive，接口吐出 `2026-09-16T13:01:51.626175`
这种没有 `Z` 的串，浏览器按**本地时间**解析，在东八区差了 8 小时。

**修法**：新增 `schemas.UtcDatetime`（`Annotated[datetime, AfterValidator(...)]`），
所有对外时间字段都用它。放在契约边界上是最省事也最不容易漏的地方——
模型与数据库保持原样，一个注解覆盖全部响应。

**为什么值得单独记一笔**：这类 bug 不报错、不影响排序、不影响任何断言，
只会让人看到错误的时间。而且它**只在「写完之后再读一次」的路径上出现**——
单看创建响应是发现不了的，必须走列表或详情。回归测试因此同时断言两条路径。

### 4.3 导航条把「首页」折成两行

五项菜单加上账号角标之后，导航条刚好贴着 980px 的宽度上限。flex 子项默认可收缩，
一旦收缩，`首页` 就被折成竖排的 `首` `页`（实测 `.nav-link` 高度 68px）。
加 `white-space: nowrap` 后回到单行 43px，且实测不溢出（`nav.scrollWidth == 980`）。

这一条与论坛功能无关，属于并行开发中新增第五项导航后暴露的既有脆弱点，
因为每个论坛页面都会显示它，所以一并修掉。

## 5. 过程中的自我纠正

**三次是测试脚本/夹具写错，一次是并发开发踩坑，都记下来**（这些都是「验证工具本身出错」，
与产品缺陷分开记）：

- 端到端脚本最初用 `Page.navigate` 跳到 `#/new` 来打开发帖表单，
  但同文档的 hash 跳转**不会重新加载页面**（也就不重新执行页面脚本），
  论坛界面里的会话/版块状态还是上一次的，于是「注册后仍然显示请先登录」
  「版块接口已经恢复正常但界面还停在错误状态」。**同一个坑踩了三次**
  （注册后、降级验证、恢复验证各一次），最后做成 `reloadForum()` 辅助函数：
  给 URL 加一个变化的查询串强制走完整加载。这不是产品缺陷，是脚本没吃透 hash 路由的生命周期。
- 加了封面之后，「拖动旋转改变画面」突然失败（两次读数一模一样）。原因是详情页顶部
  多了一张大图，3D 画布被推到**视口之外**，而 `Input.dispatchMouseEvent` 用的是视口坐标——
  按页面坐标发事件就打空了。修法是发事件前先 `scrollIntoView`。**看起来像渲染器坏了，
  其实是测试打偏了**——这类误报最耗时间，所以专门记一笔。
- 写 WebP 夹具时踩了两个坑：VP8X 的宽高前面多塞了 3 字节（应是「1 字节标志 + 3 字节保留」
  之后直接跟宽高），VP8 漏了 3 字节帧标签（导致 0x9d 0x01 0x2a 起始码落在错误偏移）。
  两个都是夹具写错、被测代码是对的。**夹具和被测代码同时错了才会互相掩盖**，
  所以这里花了时间把四种格式的头部布局逐个对着规范核了一遍。
- `serve-dist.mjs` 原来只转发 `content-type` / `set-cookie` / `cache-control` 三个响应头，
  于是「下载响应是否带 `Content-Disposition`」「封面响应是否带 CSP」在浏览器侧永远测不到。
  改成逐个转发有用响应头，但**刻意不转发 `content-encoding` 与 `content-length`**：
  Node 的 `fetch` 已经自动解压了正文，再带上 gzip 头会让浏览器把明文当压缩流解。
- **构建产物被并行开发覆盖**：端到端第一次跑通之后，仓库里的 `dist/` 在 **29 秒后**
  被另一个并行进行的改动重新构建了，`PUBLIC_API_BASE` 从验证用的代理地址变回
  `.env` 里的 `localhost:8000`。后续验证于是全部打到那个还在跑旧代码的进程上，
  表现成「版块接口 CORS 失败」——排查了好一阵才想到去看构建产物本身。
  修法：验证用 `npx astro build --outDir dist-e2e` 生成**独立产物**，
  `serve-dist.mjs` 增加可选的产物根目录参数。多人（或多 agent）同仓库开发时，
  「构建产物」也是一种会被争用的共享状态。
- 期间还遇到一次「整个测试套件突然全红」：并行开发的那位把 `backend/.env` 的
  `NAYTIA_COOKIE_SECURE` 改成了 `true`（他要在 HTTPS 隧道下验证），
  而测试客户端走的是明文 http——浏览器和 httpx 都不会把 Secure Cookie 回传给 http，
  于是**每一个登录后的用例都变成 401**，看起来像权限体系坏了。
  已有修复：`tests/conftest.py` 显式把它钉成 `false`（环境变量优先级高于 `.env`）。
  记在这里是因为这个症状极具误导性：**测试套件不应该依赖开发者本地的部署配置**。

## 6. 已知限制（如实记录）

| 限制 | 说明 |
| --- | --- |
| 无配额与限流 | 任何登录账号都能连发带附件的帖子，总占用无上限；单文件 10 MB / 封面 5 MB 是唯一硬边界 |
| 封面不压缩 | 服务端按原图保存（不引入 Pillow），全屏截图可能有好几 MB；界面提示建议压到 1 MB 以内 |
| 封面不能替换 | 只能删掉重发——帖子本身也还不能编辑。删除入口是有的（作者/管理员），不会「传错就永久留着」 |
| 颜色是示意色 | 不打包 Mojang 的贴图资源，界面已注明「按方块名生成的示意色」 |
| 超大结构会抽稀 | 可见面超过 20 万时按坐标抽稀并明说抽了多少；只在单元测试里验证过，没在浏览器里实测帧率 |
| 大文件未实测 | 10 MB / 5 MB 上限只在接口层用「上限 + 1 字节」验证过，没有拿真实的大结构、大照片跑完整链路 |
| 一个帖子各一个附件 | 需求是「上传一个文件 / 一张封面」，多图需要新的排序与布局设计 |
| `schemas_docs.py` 仍有同一时间戳问题 | 属于文档树模块，不在本次改动范围内 |

## 7. 下一步

- 若要收紧存储：按账号限制附件数量/总量，或引入对象存储——`forum_storage.py`
  是唯一要改的文件（ADR-006 的重新评估条件里已登记）。
- 若封面原图普遍太大：需要服务端缩略图（会引入 Pillow 或外部命令，属于新增依赖，
  要单独立 ADR），或在浏览器端先缩再传（会改动用户的文件，同样要明确说明）。
- 若材料清单要能「一键复制成购物清单」：属于纯前端导出，不需要动接口。
- 若要支持多图帖子：需要图片排序、布局与「封面用哪一张」的选择，是新的界面设计。

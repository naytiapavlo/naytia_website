# ADR-006 · 论坛帖子附件的存储与网页 3D 预览

日期：2026-09-16
状态：已接受
关联需求：`../01-产品范围与功能规划.md` 第 5/7 节；`../03-内容模型与工具接入协议.md` 第 3/5 节；`../04-开发测试与发布流程.md` 第 3/4/5 节；`../05-阶段计划与任务清单.md` 阶段 4 与阶段 6「论坛进阶能力（附件）」；`ADR-003`（结构文件解析器）
替代记录：无

## 背景

需求分两步到来：先是「发帖时可以上传一个 10 MB 以内的 `.mcstructure`，由项目内置的
mcstructure 解析器解析出材料清单，并做一个轻量化的 3D 渲染器在网页里把它画出来」，
随后追加「允许用户上传图片加到帖子封面」。

两件事同属一类问题（**帖子附件**），所以放在同一份 ADR 里，共用同一套存储与安全边界。
拆开看是五个问题，每一个都有值得记录的取舍：

| 问题 | 可选项 |
| --- | --- |
| 文件放哪 | 存数据库 BLOB / 落盘（内容寻址）/ 只解析不保存 |
| 材料清单谁算 | 服务端（已有 `parsers/mcstructure.py`）/ 浏览器（工具箱已有客户端 NBT 读取器） |
| 3D 数据怎么发 | 发完整体素数组 / 发服务端算好的可见面 / 发中间表示让浏览器算 |
| 用什么画 | WebGL 体素引擎（three.js 等）/ Canvas 2D 自实现 |
| 封面怎么收才安全 | 信文件名 / 信 Content-Type / **信文件头字节** |

前置约束（已有事实，不是猜测）：

- 项目已有一个经过验证的 Python 解析器（`backend/app/parsers/mcstructure.py`，ADR-003），
  以及一套独立的客户端读取器（`src/tools/mcstructure-editor/nbt.ts`），两侧都有测试。
- 工具箱的口径是「**计算在浏览器本地完成，输入不上传**」；论坛附件天然要上传，
  两者不能混为一谈（04 文档第 5 节要求明确说明）。
- 04 文档第 4 节给首屏 JS 定的 gzip 预算是 80 KB，且「不因为加入一个引擎就让每篇文章都加载它」。
- 静态托管，没有服务端动态路由，帖子详情只能靠客户端路由。

## 决定

### 1. 文件落盘，内容寻址，库里只存摘要

`backend/app/forum_storage.py` 把文件存到
`<storage_root>/structures/<sha256 前两位>/<sha256>.mcstructure`，数据库只存相对路径、
体积、摘要、清洗后的原名，以及**解析结果摘要**（`summary_json`）。路径永不出现在任何响应里。

理由：

- **BLOB 进 SQLite 会让备份和查询一起变难**：10 MB 的附件塞进 OLTP 表，任何一次
  `SELECT *` 误用都要多读几十 MB。落盘 + 只存摘要是文档树（`docs_storage`）已经用过的方案，
  这里保持一致，运维只需要关心一个目录。
- **内容寻址自带去重**：同一个结构被两个人分别发帖时磁盘上只有一份。代价是**删除要数引用**
  ——`routers/forum.py::_remove_attachment_blob` 先确认没有别的帖子引用同一个 sha 才 unlink。
  这一点单独写了测试（删掉其中一个帖子，另一个仍然能下载与预览）：直接 unlink 是那种
  「数据没错但东西没了」的难查故障。
- **只解析不保存**被排除：那样别人打开帖子时看不到任何东西，也就没有「晒作品」可言。

### 2. 材料清单由服务端用内置解析器算，浏览器不重复算

- 理由一：**清单要能被没下载文件的人看到**。让每个访客为了看一眼材料清单下载 10 MB 的
  文件（还要在浏览器里解 NBT）是不可接受的。
- 理由二：**两侧口径必须一致**。同一个文件在 `/api/mcstructure/parse` 和论坛帖子上显示
  不同的方块总数，是比崩溃更难查的问题。所以统计口径只保留一份
  （`parsers/mcstructure.py::count_blocks`），解析接口与论坛都调用它。
- 前端不重新实现解析：`src/modules/forum/` 不含 NBT 读取器。

### 3. 3D 数据发「中间表示」，不发可见面

`parsers/mcstructure_render.py` 把结构压成**占用位图 + 调色板下标数组**：

```text
occupancy: ceil(voxelCount / 8) 字节；第 i 格有方块 ⟺ occupancy[i>>3] >> (i&7) & 1
indices:   非空格子按位置下标升序排列，每个 8 位或 16 位小端整数
```

- **不发完整体素数组**：`64×256×64` 的结构是 104 万格、两层 208 万个整数，JSON 化十几 MB，
  而其中绝大多数是空气。位图让空气只占 1 bit。
- **不发服务端算好的可见面**：那样旋转、分层、剖面这些交互每次都要回服务器，
  「看一眼别人盖的房子」变成每帧一次请求。
- 折中的代价是多了一个需要两侧对齐的二进制小协议。所以布局在 Python 模块头部写死成唯一事实源，
  两侧各有独立测试：Python 侧手推期望值，TypeScript 侧由**测试自己重新编码**载荷
  （`tests/forum-voxel.test.ts::encodeGrid`），不复用生产解码器——共用一个实现的话，
  协议写错了两边会一起错。
- 载荷在上传时就 gzip 落盘（大段空气与大段同色方块压得极好），
  预览接口直接回压缩字节并按 `Accept-Encoding` 决定是否解压；配合
  `Cache-Control: immutable`，反复打开帖子不必重复压缩。

### 4. 3D 用 Canvas 2D 自实现，不引入 WebGL 引擎

`src/modules/forum/voxel.ts`（纯计算）+ `voxel-view.ts`（画布与交互），约 600 行，零依赖。

- 结构本来就是规整的立方体网格，画家算法 + 正交投影足够像样；引入 three.js 这类依赖
  与「轻量化」直接冲突，也会突破 04 文档的 JS 预算。
- 关键优化按收益排序：**剔除被邻居挡住的内部面**（实心建筑常能砍掉 80% 以上的绘制量）、
  **只画朝向相机的三个面**、**相邻同色面合并成一条路径**（体素建筑里大片同色墙体很常见，
  这是 `fill()` 调用次数从几万降到几千的一步）、**按需重绘**（没有空转的动画循环）。
- 诚实边界写在界面上：颜色是**示意色**（不打包 Mojang 的贴图资源），
  可见面数超过 20 万时按坐标抽稀并**明说抽了多少**——让人以为「结构就长这样」
  比让人等两秒更糟。

### 5. 接口形态：multipart 单独开一个端点，两个附件都可选

`POST /api/forum/threads/with-attachments`（multipart）与既有的
`POST /api/forum/threads`（JSON）并存，而不是把 JSON 端点改成双形态。

- OpenAPI 是前端类型的唯一来源（ADR-001），一个端点同时接受 JSON 与 multipart
  会让生成的契约含糊；「纯文字帖」与「带附件帖」在前端本来就是两条提交路径。
- 文本字段复用同一个 `ThreadCreate` schema，校验失败转成 `RequestValidationError`，
  两个端点吐出**完全一样**的 422 响应体，前端不必写两套字段错误解析。
- 做成一个端点而不是「先发帖再传附件」，是为了一致性：任何一个附件被拒时帖子都不会
  被创建，用户拿到一条明确的错误，而不是「帖子发出去了但附件没了」这种半成品。

**端点在加封面时从 `with-structure` 改名而来，字段名从 `file` 改成 `structure` / `cover`。**
理由：一个帖子现在有四种组合（纯文字 / 只带结构 / 只带封面 / 都带），拆成多个端点会让
前端按组合去猜该调哪个；而两个可选文件放在一起时，`file` 这个笼统的名字说不清是哪一个。
项目还没发布，没有外部调用方，所以直接改名而不是留一个名不副实的别名。

### 6. 附件是可以下载的公开资源

`GET /api/forum/threads/{id}/structure/file` 提供原始文件下载。用户愿意公开自己的建筑，
就该能被人拿走继续用。安全处理：`application/octet-stream` +
`Content-Disposition: attachment` + `X-Content-Type-Options: nosniff`，
即使有人把伪装成 `.mcstructure` 的 HTML 传上来（解析器会拒），浏览器也不会按网页执行它。

### 7. 封面：类型只信文件头字节，且拒绝 SVG

封面是全站**唯一**把用户上传的字节当「可直接渲染的内容」发出去的地方
（`<img src>` 直接指向本站 origin），所以这里的判据必须比其它地方更硬：

- **认格式只看文件头**（`parsers/image_info.py`，纯标准库）：PNG 签名、JPEG 的 SOI、
  `GIF87a/89a`、`RIFF….WEBP`。用户给的扩展名只用于显示，**绝不参与**
  `Content-Type` 的判定或落盘路径的拼接。只信文件名的实现里，
  一个叫 `cover.png` 的 HTML 会被浏览器当网页执行——存储型 XSS。
- **SVG 一律拒绝**。它确实是图片，但可以内嵌 `<script>`，浏览器按文档渲染时
  就是一段可执行内容；要支持得先做完整的消毒，那是另一个量级的工作，
  而截图/照片本来就不该是 SVG。拒绝时给出明确文案，而不是笼统的「格式不支持」。
- **认出来还要读得出尺寸**：头部合法但 IHDR/SOF 读不出来的文件按损坏处理并拒绝。
  尺寸同时用于列表排版（写进 `<img width height>`，避免图片加载完成时页面跳动）。
- **提供时三道响应头**：按入库时判定的 `Content-Type`、`X-Content-Type-Options: nosniff`、
  `Content-Security-Policy: default-src 'none'; sandbox`。最后一条是兜底：
  万一有人直接打开图片地址，它也只能作为一张图存在。
- **路径白名单按类型收紧**：`covers/<2 位>/<64 位 hex>.<png|jpg|gif|webp>`，
  正则里根本不存在 `.html` / `.svg` 的形状，即使上游校验被绕过也拼不出危险的名字。

封面**不做服务端压缩**（不引入 Pillow，与 ADR-003「零第三方解析依赖」的口径一致），
按原图保存；界面上提示建议控制在 1 MB 以内，因为列表里每次都会加载它。
这是明确的已知限制，不是遗漏。

## 数据与回退

- 数据库新增两张表：`forum_structures`（一对一挂在帖子下）与 `forum_covers`（同上）。
  `Base.metadata.create_all` 会自动建表，无需迁移；删除帖子级联删掉记录。
- **为什么封面也单开一张表，而不是给 `forum_threads` 加几列**：
  `create_all` 只建新表、**不会给已有的表加列**。往 `forum_threads` 加列会让所有
  已经存在的数据库（包括开发者本机的 `data/app.db`）在第一次查询时报
  「no such column」，而这个项目没有迁移工具。新表则是不动旧数据就能生效的。
- 磁盘上的附件是**可再生**的：删掉整个附件目录只会让预览与下载返回 410，
  帖子正文与回复不受影响。帖子删除时按引用计数清理文件。
- 停用方式：从 `app/main.py` 移除 `forum.router` 或移除相应端点即可；
  已经发出去的帖子会少掉附件面板，`has_structure` / `has_cover` 徽标随之消失，
  其余部分不受影响（符合 02 文档「云端功能失败时静态内容仍可用」）。
- 目前**没有配额与限流**：任何登录账号都可以连发带附件的帖子，总占用无上限。
  单文件 10 MB / 5 MB 是唯一的硬边界。这一条在下面的重新评估条件里。

### 一次真实的顺序缺陷

最初一次发帖写两个附件时，代码是「解析结构 → 落盘结构 → 校验封面 → 落盘封面」。
封面被拒时数据库回滚，但**结构文件已经写进磁盘**了，留下一个没有任何记录引用的孤儿文件。
测试 `test_封面被拒时结构文件也不入库` 抓到了它。

改成两段式：`prepare_structure` / `prepare_cover` 只做校验与解析（不碰磁盘），
`store_structure` / `store_cover` 只做落盘与建记录。**所有输入验完之后才开始写磁盘**，
这样任何一步被拒都不会留下半成品。

> 内容寻址下孤儿文件本身不算数据不一致（同样的内容再上传会直接复用），
> 但「每次失败上传都漏一个文件」累积起来就是没人能解释的磁盘占用——
> 这种问题查起来比崩溃更难。

## 重新评估条件

- 出现**存储配额**需求时（当前无上限）：需要按账号限流与总容量统计，
  可能要引入对象存储适配器——届时 `forum_storage.py` 是唯一要改的文件。
- 封面原图太大（用户传的都是几 MB 的全屏截图）时：需要服务端缩略图，
  那会引入 Pillow 或外部命令，属于**新增依赖**，要单独立 ADR；
  更轻的替代是「浏览器端先缩再传」，但那会改动用户的文件，同样要明确说明。
- 附件类型继续扩展（`.mcworld` 存档、视频）时：需要按类型分流解析器与预览方式，
  不要往现有的 `summary_json` 里塞异构字段；每加一种都要重新问一遍
  「这个类型的字节能不能被直接当内容渲染」。
- 若 `summary_json` 的结构随解析器口径变化而频繁调整：升级为显式列 + 迁移脚本，
  而不是继续往 JSON 里加字段（当前判断是不值当：这些字段只读不查）。
- 需要「多人协作编辑同一个结构」或「编辑已发布的帖子」时，
  内容寻址的不可变语义不再适用，需要版本模型（目前帖子发出去就不能改）。

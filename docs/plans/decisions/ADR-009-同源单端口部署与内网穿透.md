# ADR-009 · 同源单端口部署与内网穿透

日期：2026-09-16
状态：已接受
关联需求：[`14-部署手册`](../14-部署手册-域名与内网穿透.md)、阶段清单 D05（托管与域名）；
与 [`06-开发日志`](../06-开发日志-工具系统实装.md) 第 3.2 节的 Cookie 结论、
[`ADR-008`](ADR-008-AI助手代理DeepSeek与配额.md) 关于「上线到反代前必须取真实 IP」的待办直接相关
替代记录：无（首次为正式发布定下部署形态）

## 背景

到 2026-09-16，站点功能已经可用，但一直没有正式发布形态：`astro.config.mjs` 里
`site` 是空的，`05-阶段计划` 的 D05（托管与域名）仍是待办，`README` 也只写了本地开发。

本次的实际约束（由用户给定）：

- 域名在 **GoDaddy** 注册；
- **后端跑在本机**，通过**樱花的 HTTP 隧道**（内网穿透）对外；
- 与 GoDaddy 有关的交互由用户自己完成，代码侧要把其余部分准备好。

由此推出几个硬约束：

1. **前后端要同源。** 会话 Cookie 用 `SameSite=Lax`（`backend/app/routers/auth.py`），
   跨站时浏览器不会带上它；`06-开发日志` 已经明确记录「`cookie_secure=false` +
   `SameSite=Lax` 只在**同域部署**下可用，分域部署必须重新评估 Cookie 与 CORS」。
   两条隧道（一条前端一条后端）会立刻把站点变成两个来源。
2. **Astro 产物是纯静态文件**（`output: 'static'`，9 个页面），后端是长驻 Python 进程。
   隧道只能指向一个"东西"，而这两者必须同时对外。
3. **后端需要访客真实 IP**：AI 助手按 IP 配额（ADR-008，
   `backend/app/ai/router.py` 里写着「部署到反代后应改为读取可信代理头」），
   公开工具 API 也按 `ip:<地址>` 记账。而穿透链路上 socket 地址永远是 `127.0.0.1`。
4. 本机是 Windows，**不引入需要另行安装的常驻服务**（nginx/caddy 不在机器上，
   尝试获取 Caddy 二进制时其 CDN 不支持断点续传、多次卡在 1 MB）。

## 选择

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| A. 隧道 → Astro 静态服务（4321） | 一条隧道、零额外代码 | `/api` 无处可去，账号/论坛/文档树/工具 API 全部失效 |
| B. 隧道 → FastAPI（8000），让后端也发静态页面 | 一条隧道、零额外代码 | 后端要新增静态托管逻辑；HTML 与 API 的缓存、MIME、404 语义混在一起；违背「内容与展示分离」 |
| C. 两条隧道或两个子域（前端一条、后端一条） | 各自简单 | 变成跨站：会话 Cookie 被拦、要放行 CORS 预检、`SameSite=Lax` 失效；且樱花一条隧道最多绑 3 个域名，仍要额外占用隧道数 |
| D. 安装 nginx / Caddy 做反向代理 | 成熟、性能好、配置声明式 | 机器上没有；本机安装常驻服务、要处理开机自启与证书；Caddy 二进制下载在本网络拿不下来 |
| E. **用项目已有的 httpx + uvicorn 写一个同源入口**（`deploy/server.py`） | 只占一条隧道、一个端口；浏览器只看到一个来源，Cookie/CORS/相对路径全按同源处理；零新依赖；静态与 API 的分流规则可以写成测试 | 自己维护约 500 行转发代码；功能不如成熟反代全面（无 HTTP/2、无独立压缩、限流需自行实现） |

## 决定

采用 **E**：新增 `deploy/server.py`，在 `127.0.0.1:8080` 上同时承载静态产物与后端 API：

- `/api` 与 `/api/...` → 转发到 `127.0.0.1:8000`（FastAPI）；
- 其余 `GET/HEAD` → 直接读 `dist/` 下的文件，目录回落到 `index.html`，
  无斜杠目录 302 补斜杠，找不到就给站点自己的 `404.html`；
- `/_astro/*` 返回 `max-age=31536000, immutable`（文件名带内容哈希），
  HTML 返回 `no-cache`；
- 请求体**边收边转**（`.mcstructure` ≤32 MB、文档树分块上传都在这条路上），
  不落盘、不整体读进内存。

配套决定：

1. **前端 API 基地址改为同源相对路径**：根 `.env` 的 `PUBLIC_API_BASE` 置空，
   `src/shared/api-client.ts` 的兜底值也改为空串（原为 `http://127.0.0.1:8000`）。
   出问题时的表现是「线上仍试图连本机 8000」，测试用例里已钉住构建产物不含该地址。
2. **FastAPI 的接口文档让位**：站点自己有 `/docs/`（访客看的文档树），
   所以把 Swagger/ReDoc/OpenAPI 挪到 `/api/docs`、`/api/redoc`、`/api/openapi.json`
   （`backend/app/main.py`）。`/api/v1/tools` 等既有路由不变。
3. **访客真实 IP 的规则**（两侧配合）：
   - 入口侧：**丢弃**访客自带的 `X-Forwarded-For`/`X-Real-IP`/`Forwarded`，
     然后从右往左读上游（樱花 frps）追加的 XFF，跳过属于「我们自己这一串代理」的
     回环/私网地址，取第一个不属于它的地址作为访客 IP，再以单值形式写给后端；
   - 后端侧：`--proxy-headers --forwarded-allow-ips=127.0.0.1`，
     只信任回环来源，`request.client.host` 即可拿到真实 IP；
   - `X-Forwarded-Proto` 只在取值为 `http`/`https` 时采信（Cookie 的 `Secure` 属性依赖它）。
4. **隧道必须是 HTTP 类型**：樱花的 HTTP 隧道才会把访客 IP 追加到 XFF 尾部
   （<https://doc.natfrp.com/bestpractice/realip.html>），且自带自动 HTTPS。TCP 隧道两者都没有。
5. **域名是构建期配置**：根 `.env` 的 `SITE_URL` 经 `vite.loadEnv` 进入
   `astro.config.mjs` 的 `site`。站点内部一律相对路径，所以换域名只需改一行 + 重新构建。

## 扩展影响

- 新增文件：`deploy/server.py`、`deploy/test_server.py`、`deploy/start-*.cmd`、
  `docs/plans/14-部署手册-域名与内网穿透.md`、本 ADR。
- 修改文件：`astro.config.mjs`（读 `SITE_URL`）、`src/shared/api-client.ts`（同源兜底）、
  `backend/app/main.py`（接口文档路径）、`.env` / `.env.example`（新增 `SITE_URL`）。
- **接口兼容性**：`/api/*` 全部路径不变；只有后端自带的 `/docs`、`/redoc`、`/openapi.json`
  挪到了 `/api/` 下。`npm run api:types` 需要改成从 `/api/openapi.json` 取契约
  （`package.json` 里的地址待同步，见「验证」）。
- 新增工具、新增页面都不需要动这一层：静态分流按目录回落，API 分流按 `/api` 前缀。
- 未覆盖：HTTP/2、压缩（后端自行 gzip）、限流、多实例、静态内容的多级降级。

## 数据与回退

- **无数据迁移**：不新增表、不改字段。SQLite（`backend/data/app.db`）与附件目录原样使用。
- 端口变化：后端 8000、入口 8080，都是新增的对外约定，没有取代任何既有端口
  （Astro dev 仍是 4321）。
- **回退**：`git revert` 相应提交即可回到「纯本地开发」。入口是一个独立文件，
  删掉它不影响 `npm run dev` / `uvicorn --reload` 的原有开发方式；
  `PUBLIC_API_BASE` 填回 `http://localhost:8000` 就恢复跨端口开发模式。

## 验证

本机已实测（2026-09-16，命令与结果见 [`14`](../14-部署手册-域名与内网穿透.md) 第 6 节）：

- 站内 29 个 URL 全部 200，无死链；`/blog` 302 → `/blog/`；`/nope-xyz` 返回站点 404 页；
- `/docs/` 是文档树页面，`/api/docs` 是 Swagger，两者互不抢占；
- 登录「访客」账号 → 带 Cookie 请求 `/api/auth/me` 返回同一账号，会话 Cookie 经入口完整往返；
  带 `X-Forwarded-Proto: https` 时 `set-cookie` 正确带上 `Secure`；
- multipart 上传 515 字节 `.mcstructure` 夹具 → 200；
- `X-Forwarded-For: 203.0.113.77` → 后端配额身份 `ip:203.0.113.77`；
  伪造前缀 `9.9.9.9, 203.0.113.77` → 仍取尾部真实 IP；
- 目录穿越 4 种写法全部拒绝；`/apiary` 不再被误当作 API 前缀；
- `python deploy\test_server.py` 21 个用例通过（含上面这些规则）；
- 全量：`npm test` 115 项、`pytest` 332 项通过、`astro check` 0 error、构建 10 个页面；
  构建产物的 `<link rel="canonical">` 由 `SITE_URL` 生成为 `https://www.naytia.io/...`。

## 重新评估条件

- 后端不再跑在本机（迁到云主机/VPS）时：入口仍可用，但「隧道」这一环可以去掉，
  换成真正的反向代理与进程守护；届时重新评估是否仍自己维护 `deploy/server.py`。
- 需要 HTTP/2、TLS 终止、更细的限流或 WAF 时：换成 Caddy/nginx，
  本 ADR 的分流规则（`/api` 前缀 + 目录回落 + 缓存策略）可以直接照搬。
- 访客量或上传量超出单进程异步转发的承受范围（`deploy/server.py` 是单进程，
  连接池 64）时：需要多进程/多实例，配额随之必须改成 Redis 或数据库计数
  （与 ADR-008 的「多实例部署」条目同时失效）。
- 樱花改为只提供 TCP 隧道、或改用其它穿透服务不追加 XFF 时：
  第 3 条的真实 IP 规则要重做（退回 socket 地址或改用 Proxy Protocol）。

# ADR-003 · 基岩版结构文件（.mcstructure）解析器的实现方式

日期：2026-09-16
状态：已接受
关联需求：`../01-产品范围与功能规划.md` 第 5/6 节；`../03-内容模型与工具接入协议.md` 第 3 节；`../04-开发测试与发布流程.md` 第 3/5 节；`../05-阶段计划与任务清单.md` 阶段 6「文件导入导出」
替代记录：无

## 背景

需要为网站增加一个独立的 `.mcstructure`（Minecraft 基岩版结构文件）解析能力，并以接口形式提供，
解析深度要求覆盖**完整结构 + 实体 + 方块实体 NBT**。

`.mcstructure` 的技术特征决定了可选项：

| 特征 | 取值 | 影响 |
| --- | --- | --- |
| 编码 | NBT（Named Binary Tag，标签树） | 需要一个 NBT 读取器 |
| 字节序 | **小端**（Bedrock 口径；Java 是大端） | 大端实现不能直接用 |
| 压缩 | 官方不压缩（用户常拿到 gzip/zlib 副本） | 需按魔数识别并解压 |
| 结构 | 根复合标签 `format_version` / `size` / `structure` | 需一层语义解析 |
| 坐标 | `block_indices` 按 **ZYX** 顺序展开，两层共位，`-1` 为 void | 下标换算必须与文档一致 |

现有可选实现（调研于 2026-09-16）：

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| A. `nbtlib`（Python，MIT） | 纯 Python；`File.parse(..., byteorder='little')` 支持小端；活跃维护 | 需要新增依赖；本机 PyPI 直连不通 |
| B. `rapidnbt`（已装，MPL-2.0，含 C++ 内核） | 性能好 | **实测 `to_binary_nbt()` 输出大端**；pybind11 版 `NbtFile` 无公开构造函数、无法指定小端文件格式 |
| C. `bedrock_protocol.nbt`（已装，包装 B） | 名义上面向 Bedrock | **当前版本 import 即失败**：`ImportError: cannot import name 'Int64Tag' from 'rapidnbt'` |
| D. `amulet-nbt`（PyPI，C++/pybind11） | 生态成熟（Amulet 编辑器在用） | 已装版本 2.1.8 的 `load()` 没有 `little_endian` 开关，实测读不了小端文件 |
| E. 自实现小端读取器 | 无新依赖；字节序/上限/错误分类完全可控；约 200 行确定问题 | 需要自己保证正确性，靠独立夹具与测试覆盖 |

同时本机网络受限：PyPI 直连与 GitHub 均超时，仅镜像 `mirrors.aliyun.com` 可用
（因此即便选 A/D，也要指定镜像安装）。

## 决定

**自实现小端 NBT 读取器**（`backend/app/nbt_le.py`，约 260 行，只用标准库 `struct`/`zlib`），
结构语义层另写（`backend/app/parsers/mcstructure.py`），**不新增第三方解析依赖**。

理由：

1. 候选库中已装的三个（B/C/D）经实测**都不能读小端 NBT 文件**，唯一可用的 A 需要新增依赖。
2. 小端 NBT 读取是**边界清晰的确定问题**：12 种标签类型、长度前缀、嵌套复合。
   自实现的收益（零依赖、字节序明确、资源上限与错误分类可控）大于风险。
3. 04 文档第 3 节要求「损坏/截断、错误码版本、超大声明长度、压缩膨胀」必须有明确行为——
   自实现才能在**读取之前**就按上限拒绝，而不是先分配再失败。
4. 正确性不靠自我声明：夹具由**独立于被测代码**的写入器生成
   （`backend/tests/fixtures/mcstructure_fixtures.py`），并用第三方实现 `nbtlib`
   在离线校验模式下复读（`--check`），确认夹具本身是合法小端 NBT。夹具若有错，
   被测读取器与 nbtlib 会在同一偏移处失败，能立刻暴露（开发过程中确实靠这一点定位了夹具错误）。

存储与接口形态：

- 新增只读接口 `POST /api/mcstructure/{parse,voxels,slice,position,blocks}` 与 `GET /api/mcstructure/info`。
- **索引与体素分离**：`block_indices` 是完整方块数组（64×256×64 就有 104 万个数），
  因此 `/parse` 默认只返回索引与统计，体素需显式 `include_voxels=true` 或走 `/voxels`、`/slice`。
- 上传内容**不落盘、不写日志**；响应不回显文件名以外的上传元数据。
- 未建模字段保留（`raw_nbt` / `extra_root_fields`），不静默丢弃。
- 越界调色板下标按游戏口径视为空气，但在统计里**单列计数**，不替用户改写数据。

## 扩展影响

- `03` 契约新增一组只读接口；前端类型仍由 OpenAPI 生成（`npm run api:types`），
  前端模块 `src/modules/mcstructure/` 只从 `src/ports/api-schema.d.ts` 取类型，不另写字段定义。
- `04` 第 5 节「文件处理明确说明是否上传」：本接口**要求上传**（服务端解析），
  与工具箱「计算在浏览器本地完成」的默认口径不同，已在 `/info` 接口与前端模块注释里写明。
  若后续要改成本地解析，需另立 ADR：届时可复用同一套格式规则与测试夹具。
- 若将来需要写入/生成 `.mcstructure`，需在本模块补充**小端序列化器**并单独立测试；
  当前只做只读解析，不提供下载或写回。

## 数据与回退

- 无持久化：解析在请求内完成，不写数据库、不留缓存，因此没有数据迁移与回退问题。
- 停用方式：从 `app/main.py` 移除 `mcstructure.router` 即可，站点其余部分不受影响
  （符合 02 文档「云端功能失败时静态内容仍可用」）。
- 资源上限可调：`NAYTIA_MCSTRUCTURE_MAX_BYTES`（默认 32 MB）、
  `NAYTIA_MCSTRUCTURE_MAX_VOXELS`（默认 16,777,216）。

### 真实文件暴露的格式偏差（重要）

用真实文件核对时发现：**`structure_world_origin` 的实际层级与文档不一致。**

- [bedrock.dev 文档](https://wiki.bedrock.dev/nbt/mcstructure)：写在 `structure` 复合体**内部**。
- 真实文件：写在**根层级**，与 `format_version` / `size` 同级（该文件取值 `[72, 59, -10]`）。

旧实现只按文档查 `structure` 内部，结果是**解析不报错、但原点静默变成 `None`**——
属于最难发现的一类 bug（没有异常、没有错误码，只是少了一个字段）。

修正：两处都探测，并用 `world_origin_source`（`'root'` / `'structure'` / `None`）标明来源；
并把 `structure_world_origin` 加入「已消费字段」集合，避免它同时出现在 `extra_root_fields` 里。

交叉验证：该文件方块实体 `PistonArm` 的 NBT 里 `x/y/z = 72/59/-10`，与结构原点完全一致
（那是该方块的绝对世界坐标），因此「结构原点」与「方块实体 NBT」两条读取路径互相印证。

**教训**：手工夹具（即使完全按文档写正确）也无法发现「文档与真实实现不一致」。
凡解析外部二进制格式，都必须留一份真实样本做回归——这条已写进
`backend/tests/fixtures/real/README.md` 的约定里。

## 重新评估条件

- 出现「写回 / 生成 .mcstructure」需求时（需要补序列化器，不只是读取器）。
- 需要解析其它 Bedrock 二进制格式（如 LevelDB 存档、`.mcworld`）时，
  应扩展现有 `nbt_le` 而不是再写一个平行实现。
- 若将来网络与依赖治理允许，且 `nbtlib` 一类成熟库能满足小端 + 上限控制，
  可以用「更换适配器」的方式替换自实现读取器，接口与测试保持不变。

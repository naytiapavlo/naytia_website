# ADR-010 · 账号管理界面：搜索放服务端、管理员开关单独开接口、超管档位不在这里改

日期：2026-09-16  
状态：已接受（用户要求：给超级管理员增加一个管理用户列表的界面，可以设置管理员或者取消管理员，要能根据名字搜索）  
关联需求：`../01-产品范围与功能规划.md` 第 7 节（权限）；`../02-总体架构与扩展规范.md`；

替代记录：无（`ADR-002` 只定了「超管可以改他人角色」，没定改的入口与形态）

## 背景

ADR-002 落地时已经有两个后端接口：`GET /api/admin/accounts`（列出账号）与
`PUT /api/admin/accounts/{id}/role`（写任意角色）。也就是说，**能力早就在**，
缺的是「站长实际怎么用」——当时唯一的用法是直接调 API 或看数据库。
随着站上账号变多，「谁现在是管理员、把谁提上去、把谁的权限收回来」变成了
一件需要带界面的日常工作。

要求的原话是：管理用户列表 + 设置/取消管理员 + 按名字搜索。三个动作背后
各有一个必须先定的问题：

1. **搜索在哪一端做**：列表接口一次返回全部账号，前端过滤是最省事的做法；
2. **「设为管理员」是不是就是「把 role 写成 admin」**：现成的 `/role` 接口收
   任意角色（含 `superadmin`），前端拼一个 `role: 'admin'` 就能用；
3. **超管的档位能不能在这一页动**：数据上超管也是 `accounts.role` 的一个取值。

## 选择

### 一、搜索放服务端还是客户端

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| A. 服务端过滤（`?q=`，SQL LIKE） | 结果永远与搜索词匹配，与「已加载了多少」无关；账号增长后仍然正确 | 每次输入要发请求（用防抖 + 请求序号收敛）；要处理 LIKE 通配符转义 |
| B. 前端过滤已加载的列表 | 零请求、零延时，输入即出结果 | 只在「已经拿到的那一批」里找；一旦将来分页或截断，搜不到就会得出「这个人不存在」的错误结论 |
| C. 服务端过滤 + 前端复筛当前批 | ——（A 的体验 + B 的即时感） | 两处匹配口径要保持一致（靠同名规则 + 两侧各一组测试钉住） |

**决定 C**：口径以服务端为准，前端只对「当前这一批」做即时复筛（输入到服务端
结果返回之间，界面不会留着明显不匹配的行）。匹配规则两边一致：大小写不敏感的
用户名子串匹配。服务端转义 `_` / `%` / `\`——不转义的话搜一个下划线会命中所有
账号（`_` 在 LIKE 里是「任意单字符」），管理界面里就成了「搜什么都有」。

### 二、「设为管理员」单独开接口还是复用 `/role`

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| A. 复用 `PUT /accounts/{id}/role`，前端拼 `role` | 不加接口、不加契约 | 一个「给不给管理员」的开关，因此拥有把别人写成 `superadmin` 的能力；权限来自界面的自觉，而不是契约 |
| B. 新增 `PUT /accounts/{id}/admin`，体为 `{"enabled": bool}` | 契约层面就把这条路径锁在 admin ↔ member 两档；`enabled` 还能用 `strict=True` 挡住 `"false"` 这类真值陷阱 | 多一个路由、多一个 schema；与前一个接口职责部分重叠 |

**决定 B**。理由不是「更安全一点点」，而是**最小权限应当写在契约里**：界面要做的
是「开关管理员」，那么它拿到的接口就应该只做这件事。`/role` 保留给「调整角色」
这类更强的场景（它带上了最后一个超管的兜底判断），两者共用同一段目标校验。

顺带修掉一个真实的坑：`enabled: "false"` 在宽松转换下会变成「设为管理员」——
Python 里非空字符串是真值，这是权限系统里最不能出的一类错。契约上写
`strict=True`，让它在 422 就失败。

### 三、超管档位在这一页能不能动

| 方案 | 收益 | 成本与限制 |
| --- | --- | --- |
| A. 允许（超管可被降为 admin/member） | 「管理员开关」语义完备 | 超管本来就拥有管理员的全部能力，降级是纯粹的权限损失，只可能来自误操作；且降级会连带失去站点配置与账号管理入口 |
| B. 禁止，并说明原因（超管档位只由引导规则/邀请码产生） | 误操作不可能造成超管流失；界面上不出现「点了必然失败」的按钮 | 真要调整超管档位时得走 `/role` 或直接改库；「取消管理员」按钮对超管行不存在，需要文案解释清楚 |

**决定 B**（响应 `is_superadmin`）。同时保留并明确了两条既有的自改保护：
超管不能改**自己**的角色（`self_role_change`，ADR-002 已定）。这两条合起来
就是「场上永远至少有一个超管」——因为能做到「把最后一个超管降级」的路径，
必然要么是改自己（被拦），要么是把目标改成非超管（而目标就是最后一个超管，
他自己的档位一改就没了唯一性）。`/role` 里那道 `_superadmin_count <= 1` 判断
因此是**第二层兜底**：当前不可达，等哪天放开「超管可以改自己」时它才成为主力。

## 决定

1. **接口**（`backend/app/routers/admin.py`）
   - `GET /api/admin/accounts?q=`：账号列表 + 可选搜索；不传 `q` 时语义不变
     （按 id 升序，注册最早的在前，也就是超管自己）。
   - `PUT /api/admin/accounts/{id}/admin`：`{"enabled": bool}` → admin / member。
   - `PUT /api/admin/accounts/{id}/role`：保留原语义，补上「最后一个超管」兜底。
   - 三条都在 `require_superadmin` 之下；「改自己」与「动超管档位」共用
     `_writable_target`，避免其中一条路径漏判。
2. **页面**：`/admin/users/`（`src/pages/admin/users.astro`），模块
   `src/modules/admin-users/`（`api.ts` / `rules.ts` / `ui.ts`，唯一入口 `index.ts`）。
   超管的导航栏在登录后插入「账号管理」入口（`mountAdminNav`），普通会员与访客看不到。
3. **前后端同规则**：`rules.ts` 的 `rowCapability` 与 `matchesSearch` 对应服务端的
   `_writable_target` 与 `_like_pattern`，两侧各有独立测试（前端 18 项、后端 16 项）。
   前端那一道只是「不让人点了才失败」，**不是**权限边界。
4. **契约先行**：`src/ports/api-schema.d.ts` 由后端 OpenAPI 重新生成（ADR-001），
   前端类型从 `components['schemas']['AccountSummary']` 取，不手写字段。
5. **超管档位只由引导规则与邀请码产生**（沿用 ADR-002），这一页不提供授予或取消超管的入口。

## 扩展影响

- `BaseLayout` 增加一个客户端挂钩（`mountAdminNav`）：静态导航 `site.nav` 不写
  「账号管理」，因为它对访客无意义，而 `site.nav` 是构建期配置、访客也能拿到。
- `src/modules/account/roles.ts` 从 `account/api.ts` 里拆出纯词表（`Role` 与
  `ROLE_LABELS`，零 import）。原因很具体：`npm test` 用 `node --test` 跑 `.ts`，
  是「只删类型」模式，而 `shared/api-client.ts` 的 `ApiError` 用了构造函数参数属性，
  属于该模式明确不支持的语法——任何 `import ... from './api'` 的纯逻辑文件都会
  在测试里直接编译失败。拆开后纯逻辑可测，`account` 的公开接口不变。
- 后续若增加角色档位（例如「版主」），需要同时改后端 `ROLES`、`_writable_target`
  的分支与前端 `roles.ts` 的词表；`rowCapability` 是按档位显式判定的，不会静默放行。

## 数据与回退

- **无数据库结构变更**：用的是 `accounts.role` 与新增的查询参数，不需要迁移。
- 回退：停用 `/api/admin/*` 路由后，`/admin/users/` 会显示「账号列表没能加载」
  并提供重试；导航入口与页面其余部分不影响静态站（其余页面照常）。
- 权限不回退：接口全部在服务端判定，无论前端怎么改，member 拿不到列表、也改不了角色。

## 验证

- `backend/tests/test_admin_users.py` **16 项**：搜索（子串 / 大小写 / 无匹配 /
  通配符转义 / 不传 q 的语义 / 仅超管）、授予与收回、提权后真的能审核删帖、
  非超管 403、未登录 401、不能改自己、`/admin` 不触碰超管档位、未知账号 404、
  `enabled` 必须是真的布尔、另一超管可以降级超管（守卫按「会不会拿掉最后一个」判断）。
- `tests/admin-users.test.ts` **18 项**：匹配口径（含正则元字符按普通字符处理）、
  角色文案、`rowCapability` 的三条分支与优先级、确认话术、分档计数。
- `tests/manual/verify-admin-users.mjs` **24 项浏览器链路**（真 Chrome + 真后端 +
  真 Astro 服务，隔离库）：未登录/会员/超管三种身份看到的界面不同、导航入口只在
  超管出现、列表与角色徽章、搜索（本地复筛 + 服务端结果）、授予后徽章就地翻转并
  刷新仍在、取消后回到会员、确认框选「取消」时不发请求、退出登录后入口消失、
  控制台无错误。
- 回归：`backend/` pytest **303 项全绿**、`npm test` **115 项全绿**、
  `npx astro check` 0 error；浏览器链路连跑三次结果一致、无残留进程与临时目录。

> 一个**既有**问题在验证过程中被记下来（不是本次改动引入）：
> `backend/.env` 的 `NAYTIA_COOKIE_SECURE=true` 让明文 http 下的测试客户端永远拿不到
> 会话 Cookie，58 项登录相关用例因此变成 401（看着像权限体系坏了）。已在
> `backend/tests/conftest.py` 里用 `os.environ.setdefault("NAYTIA_COOKIE_SECURE", "false")`
> 钉住夹具环境（环境变量优先级高于 `.env`），那批用例恢复正常。
> 其余细节见 `../15-开发日志-账号管理页.md` 第 7 节。

## 重新评估条件

出现以下任一情况时重新评估：账号规模需要分页或按角色/时间筛选（`?q=` 的形态不够用）、
需要「封禁账号」这类新状态（现在的开关只有「是不是管理员」两个方向）、
或站上出现多个超管并需要交接流程（届时「超管不能被改」这条要连同交接一起重新设计）。

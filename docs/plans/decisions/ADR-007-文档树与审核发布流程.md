# ADR-007 · 文档树的存储、可见性与「提交—审核—发布」流程

日期：2026-09-16
状态：已接受
关联需求：`../01-产品范围与功能规划.md` 第 5/7 节；`../02-总体架构与扩展规范.md` 第 4/5 节；
`../03-内容模型与工具接入协议.md` 第 2/3 节；`../04-开发测试与发布流程.md` 第 3/4/5 节；
`ADR-002`（角色权限）、`ADR-006`（附件落盘与内容寻址）
替代记录：无

## 背景

需求是「工具箱里加一个文档树工具，文档对访客可读，管理员可以编辑、新建文件夹；
管理员不需要编辑界面，给他们上传权限就行；提交合并请求给超级管理员审核，
审核通过后才真正对访客开放」。

拆开来是四个必须现在定的问题：

| 问题 | 可选项 |
| --- | --- |
| 目录树怎么存 | 邻接表（`parent_id`）/ 物化路径（`path`）/ 嵌套集合 / 闭包表 |
| 正文放哪 | 数据库 TEXT / 落盘文件 / 两者都存 |
| 谁能看什么 | 只有「已发布」一个开关 / 再加一层可见性维度 |
| 管理员改了怎么生效 | 直接改线上 / 存草稿等审核 / 生成 diff 让人手工合并 |

前置约束（已是事实）：账号体系有访客 / member / admin / superadmin 四级（ADR-002）；
站点已经有「内容寻址落盘 + 库里只存摘要」的先例（ADR-006），运维只需要盯一个目录；
站点的默认口径是「工具在浏览器本地算、输入不上传」，而文档树天然要上传，必须在界面上写清楚。

## 决定

### 1. 目录树用邻接表 + 物化路径，不做递归查询

`doc_folders` / `doc_documents` 各存 `parent_id`，同时冗余一个 `path_key`
（`'代码机制分析/12 加载源与优先级'`，同级唯一）。理由：

- **物化路径换来两件具体的事**：同级重名一眼能查（唯一索引直接拦），
  「把库里已有的 120 篇文档按路径认出来」在导入脚本里就是一次 `WHERE path_key = ?`，
  不需要按父目录逐级查或递归 CTE。
- **不选闭包表 / 嵌套集合**：那是为「子树频繁移动 + 超大深度」准备的，
  这里的规模是一个人的研究笔记（首版 8 个文件夹、120 篇文档），
  多一张表维护一致性的成本换不来收益。
- **代价如实记录**：移动/重命名文件夹需要连带重写子树的 `path_key`，
  实现集中在 `review_flow.rewrite_folder_paths()` 一处（第 5.1 节说明了不做会怎样）。
  首版不提供移动与重命名；第二轮需求追加了移动与删除，于是这段代价正式被触发并补上了测试。

### 2. 正文存库，原始文件同时落盘

`doc_revisions.body` 存正文文本，`doc_files` 同时保留原始文件（内容寻址，同 ADR-006）。
两处都存是有意的：

- **搜索要有正文**。访客搜索是服务端子串匹配（`LIKE '%关键词%'`），
  120 篇 87 万字节的量级下完全够用，前提是正文在库里，而不是每次去读磁盘。
- **版本要能回溯**。目录树上「谁在什么时候把这篇改成了什么」是有意义的信息，
  修订记录（`doc_revisions`）每发布一次追加一条，`current_revision_id` 指向当前版本。
- **下载要走原文件**。访客下载的是他上传的那份字节，不是我们重新拼出来的文本，
  所以落盘文件必须留着，`sha256` 去重让重复内容只占一份。
- 首版**只收文本**（`.md` / `.txt` / `.json`）。二进制（图片、PDF）会带来缩略图、预览、
  病毒扫描一整条链路，这一版不碰；`docs_storage.ALLOWED_EXTENSIONS` 是唯一的事实源。

### 3. 可见性与发布状态是**两个**维度

| 维度 | 取值 | 作用 |
| --- | --- | --- |
| `visibility` | `public` / `members` / `staff` | 谁能读：访客 / 登录会员 / 管理员以上 |
| `is_published` | `true` / `false` | 内容是否已经通过审核对外生效 |

- 需求只要求「访客可读 + 审核后开放」，但把「谁能读」和「是否发布」压进一个字段，
  以后想加一篇「仅内部」的文档就得再改一次表。两个正交维度，各管一件事。
- 过滤规则只写在一个地方：`routers/docs.py::Viewer`。目录树、正文、搜索、下载
  四条读取路径全部走它，避免出现「目录里看不到但拿到 id 就能下载」这类漏洞
  ——这一条有专门的测试（`test_download_of_unpublished_document_is_hidden`）。
- **未发布的内容只有两类人能看见**：staff（他们是审稿人）与提交人自己（要能确认自己交了什么）。
  这个判断集中在 `Viewer.sees_drafts_of()`。

### 4. 管理员不直接写线上，改动一律走提交单

凡是管理员发起的写操作（上传文档、新建文件夹、申请删除），都写一条 `doc_submissions`，
**不碰** `doc_folders` / `doc_documents` / `doc_revisions`。超管在待审队列里批准时才调用
`review_flow.apply_submission()` 真正落库。理由：

- 这是需求的原话（「提交合并请求给超级管理员审核再实际开放给访客访问」），
  实现上就必须有一条**与线上内容分离的提案记录**，否则「审核」只是一个开关。
- **批准时要能二次校验**。提交单可能在队列里躺几天：期间目标文档可能被删、父目录可能被改、
  同名路径可能被另一次提交占掉。这些情况在 `apply_submission` 里翻译成结构化 409，
  由路由把提交单标成 `rejected` 并写明原因（`review_note` 前缀「发布时校验失败」），
  而不是写坏目录树。测试覆盖了「批准时父目录已删」与「同名文件夹已存在」两条。
- **同一目标不允许叠加提交单**（409 `submission_conflict`）：两条都批准时后一条会覆盖前一条，
  与其让超管对着两条看起来都对的单子猜，不如在提交时就拦住。
- **删除有爆炸半径上限**：批准「删除文件夹」会连带删除子树，`MAX_CASCADE_DOCUMENTS = 200`
  是刻意的刹车——选中根目录点批准就清空整个知识库，是那种点错了没法撤销的操作。
- 提交单的**列**存发布时必须的字段（`file_id` / `title` / `parent_id` / `target_id`），
  `payload` 只放正文这种不便建列的东西。早期版本把 `file_id` 塞进了 payload，
  结果「更新文档」静默地发布了旧内容——现在有测试盯着这条路径
  （`test_update_document_creates_new_revision`）。

### 5. 首版明确不做的三件事

| 不做 | 原因 |
| --- | --- |
| 管理员**富文本编辑**界面 | 需求原话是「管理员不需要做编辑界面，只需要给他们上传文件的权限」 |
| 站内 diff / 行级对比 | 超管批准的依据是标题、摘要、上传者、正文预览与文件名；行级 diff 是另一个功能 |
| 删除时清理磁盘文件 | 文件按内容寻址，同一份内容可能被别的文档引用（与 ADR-006 的附件同理）；孤儿文件留给将来的清理任务 |

驳回与撤回必须留理由（驳回理由写进 `review_note`，作者在自己的提交列表里能看到），
否则提交人不知道该怎么改。

### 5.1 移动与删除：按角色分岔，不按功能分岔（2026-09-16 追加）

第一版把「移动 / 重命名文件夹」列为不做（要连带重写子树 `path_key`）。
第二轮需求追加了「删除文档」与「把文档移动到某个文件夹」，于是这两件事正式实装，
并确定了一条**必须记住的分岔方式**：

| 操作 | 管理员 admin | 超级管理员 |
| --- | --- | --- |
| 移动文档 / 文件夹 | 提交单（`move_doc` / `move_folder`） | 直接生效 |
| 删除文档 / 文件夹 | 提交单（`delete_doc` / `delete_folder`） | 直接生效 |
| 改标题 / 改文件夹名 | 不做 | 直接生效 |

理由：

- **分岔点在角色，不在功能**。如果按功能分岔（「移动要审核、删除不用」），
  权限模型会变成一张需要逐个功能维护的表，而 ADR-002 已经把四级角色的语义定清楚了：
  能审核的人可以直接做，不能审核的人提交等审核。
- **两条路径共用同一批实现**：管理员提交单批准后走 `review_flow.apply_submission()`，
  超管直接操作走 `direct_actions`，但两者最终都调用 `review_flow` 里的
  `move_document` / `move_folder` / `rename_document` / `rename_folder` /
  `rewrite_folder_paths`。两条独立实现迟早漂移，而漂移出来的差异
  （例如一边改了子树路径、另一边没改）是最难查的一类缺陷。
- **超管的直接操作也写一条 `status=approved` 的提交单**作为审计记录：
  目录树是多人共用的东西，「谁在什么时候把这批文档挪走了」必须查得到。
- **物化路径的代价在这一轮真正被触发**：移动或重命名文件夹必须重写整棵子树的
  `path_key`（`rewrite_folder_paths()` 是唯一实现）。不改的后果不是报错，
  而是文档的 `path_key` 指向一条已不存在的路径——**导入脚本认不出它们，
  下次按路径匹配时又插一份**，变成同一篇文档在库里有两份。
- **不允许把文件夹移进自己或自己的子树**（`move_into_self`）：子树会成为孤岛，
  显示路径算不出来、子树遍历会死循环。提交时与发布时各校验一次（提交单可能在
  队列里躺几天，期间目录结构会变）。
- **移到已有同 slug 的目录时自动加 `-2` 后缀**，不覆盖目标目录里的同名文档。
- 移动**不产生新修订**：位置不是内容，`parent_id` / `path_key` 改了就行，
  修订链与正文不动，历史仍然可回溯。

### 6. 首版资料用「导入脚本 + 超管署名」落地

`backend/scripts/import_docs.py` 把本机资料目录（默认 `C:\Users\Administrator\Desktop\Minecraft\doc`）
里的 md/txt/json 收进文档树：

- **幂等**：按 `path_key` 认文档，再次运行不会重复；只有源文件内容变了才追加一个新版本。
- **等价于超管审核通过**：脚本以超管身份运行，写进去的内容**直接是已发布状态**，
  与「超管自己上传」是同一条语义。管理员之后上传的内容仍然要走第 4 条的流程。
- **署名用真实账号**：`--imported-by` 默认取首个超管；找不到超管就退出并提示先注册，
  不伪造一个 `system` 账号——审计记录里出现一个不存在的用户比没有记录更糟。
- 导入前必须确认落盘文件真的在（`_blob_exists`）。库里有一条同摘要记录、磁盘上文件却被删了
  （清理存储、换机器、恢复备份不全）时，复用那条记录会得到一个打不开的文档。

## 后果

- **正面**：审核是流程而不是开关；权限判定只有一处；正文可搜、版本可回溯、原文件可下载；
  目录树与读路径相互独立，将来加「仅内部」文档或换存储都不需要动读路径；
  整理目录（移动 / 重命名 / 删除）对管理员是申请、对超管是立即执行，
  两条路径共用同一批实现，行为不会漂移。
- **代价**：多了三张表（提交单、修订、文件）与一条「提案 → 批准 → 落库」的状态链；
  超管成了发布链路上的单点（首版可接受，需求就是一个人审）；
  移动 / 重命名文件夹必须连带重写子树 `path_key`，这段代码是目录树里最需要小心的一处。
- **已知限制**：无上传配额与限流（靠 `NAYTIA_DOCS_MAX_BYTES` 与 staff 门槛兜底）；
  管理员不能自行改标题或重命名文件夹（这两项只在超管侧）；
  移动不产生修订记录（位置不是内容）；删除不清理磁盘上的内容寻址文件；
  不做行级 diff。

- 后端：`backend/tests/test_docs.py`（34 项）覆盖权限矩阵、审核流、上传边界、
  可见性绕过，以及移动 / 重命名 / 删除（含子树路径重写、移进自己子树、同名 slug、

  → 管理员提交移动、超管批准生效 的完整链路。
